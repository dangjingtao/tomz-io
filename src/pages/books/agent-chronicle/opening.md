# 开卷说明｜从会聊天，到真正做事

2022 年，如果请聊天模型订机票，它大概会列出一份步骤：打开网站、选航班、填乘机人信息、付款。

2026 年，同样的要求可能意味着另一套工作：理解行程，查可用航班，调用工具，处理日历冲突，检查预订结果；遇到付款或超预算的决策，再请求人的确认。

这段变化并非只因为模型变聪明了。它也依赖一整套围绕模型的配套能力：指令、上下文与记忆、工具、运行循环、反馈验证、执行环境和交付界面。这套系统，在我们采用的教材框架中叫作 **Harness**。

**这门课想讲清楚：Agent 为什么发展成今天这样，以及我们现在该如何设计它。**

## 这是怎样的一门课

《AI Agent 编年史 · Mira 研习课》面向**开发者与产品经理**。它不是一个热门框架安装合集，也不是从头到尾复述某本书。

我们从 Agent 的历史出发，每一次技术演化都追问三个问题：

1. **为什么会出现这项技术？** 它替谁解决了什么真实困难？
2. **有什么代价和边界？** 它把复杂性消除了，还是转移到了别处？
3. **今天还应该怎样使用？** 面对真实业务，哪些场景需要 Agent，哪些只需要确定性程序或受控工作流？

课程会同时提供两个视角。开发者关心架构、协议、权限、状态、恢复与测试；产品经理关心用户价值、交付体验、成本、组织协作和失败责任。面对的是同一个案例，不是两套相互分离的教材。

## 我们怎么上课

**由 Mira 讲解，不把阅读任务甩给学生。**

每节课以可缩放的 **SVG 图解**开始，用历史事件、技术结构或真实产品问题引入概念。接下来是完整讲授、双视角的案例分析，以及可以打断和追问的讨论。

你可以问：当年的 AutoGPT 为什么令人兴奋？MCP 到底解决什么，为什么不直接调 REST API？让 Agent 使用 GUI，究竟比 API 更先进还是更脆弱？

这些背景问题都值得认真回答。但每次深入追问，我们都要回到当前章节的**主线锚点**，而不是任由一次学习变成漫无边际的闲聊。

课程以小单元推进。难点可以讲透；熟悉的知识可以快速通过。它要照顾忙碌的实践者，而不是要求大家先读几十页资料才有资格提问。

## 课后必须有真题

每讲规划四道题：**概念辨析、架构或产品决策、故障诊断、综合实践**。其中两道是核心练习，两道可以进阶挑战。

题目必须有业务背景、明确约束和可检验的交付结果。不以「背出 Harness 七部件」作为所谓的工程能力考核。

例如：一家电商拥有订单查询和退款接口。退款超过 200 元必须人工审批；接口可能超时；客户留言中可能夹带恶意指令。你会把哪些环节交给确定性工作流，哪些交给 Agent？如何防止越权、重复退款，以及把一次 HTTP 成功误报成业务完成？

参考答案不必只有一种，但每个答案都应该能说清 **决策理由、失败边界与验收证据**。Mira 会据此点评，而不是只给一个对勾。

## 读完之后，应该能做什么

希望你不只是知道什么叫 MCP、Skills、Computer Use。

当一个团队说「我们要上 Agent」时，你应该能够继续追问：为什么是 Agent？它要替人完成哪段工作？什么情况下必须停下来？出了错谁来承担？我们拿什么证据说它真的完成了？

**这就是这门课的学习目标：用历史认识技术，用判断指导实践，用证据定义交付。**
