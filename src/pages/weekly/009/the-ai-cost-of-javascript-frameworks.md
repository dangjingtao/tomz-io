# 当 AI 写代码，框架还在替谁省事？

假如有一天，我们不再亲手写大部分代码，那些曾经让程序员爱上某个框架的理由，还剩下多少？

React 的组件写法、Vue 的响应式系统、Angular 的完整工程体系，它们各有拥护者。过去十几年，前端社区花了许多时间争论哪一种更优雅、哪一种更容易维护、哪一种开发体验最好。许多理由并非毫无价值，但其中总有一些很难脱离个人手感：我喜欢这样写，我的团队习惯这样写，所以它应该更好。

现在，写代码的人可能换了。

2026 年 10 月 28 日，Web 工程师 Nolan Lawson 发表了 [《The AI cost of JavaScript frameworks》](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)。他没有再问程序员喜欢什么，而是把同一份需求交给编程智能体，让它用十二种技术栈各写一遍，再数一数时间、Token、钱和交付结果。

结果里成本最低的是 Hono + htmx。

但如果读完只记住“htmx 赢了 React”，几乎就错过了整篇文章。

## 同一份需求，十二种写法

Lawson 设计的任务，是一款基于 Pokémon 数据的图鉴网站。它要展示角色、属性和招式，允许用户搜索、筛选、浏览详情。应用并不复杂，却也不只是一个静态首页：数据必须通过 API 获取，不能在构建时把所有页面预先生成出来。

他使用 Claude Opus 5.5 的高推理强度模式，让 Agent 在隔离容器里按同一份规格完成开发。测试程序检查真实页面是否符合需求，而不是只看 Agent 最后有没有自称“做完了”。应用还会接受 Lighthouse 的移动端性能和无障碍测试。

每个技术栈通常运行五次，最后取中位数。研究者公开了 [Benchmark 仓库、测试脚本与复现说明](https://github.com/nolanlawson/agent-framework-benchmark)，而且没有告诉 Agent：你正在参加一场框架性能比赛。

这一设计最值得称赞的，不是它完全公平——它显然做不到——而是它试图让框架之争离开“我觉得”，进入可以核对的工程现场。

## 一份出人意料，又并不夸张的账单

![Nolan Lawson 框架实验：一次从零构建的估算模型成本](/assets/jianpi-009-framework-cost.svg?v=009-1)

先看每次从零开发应用的估算模型费用。以下数值为五次运行的中位数；Angular 有两次没有产出可供性能测量的应用，但成本统计仍包含五次。

| 技术栈 | 单次开发成本 | 客户端 JS | 源代码行数 |
| --- | ---: | ---: | ---: |
| Hono + htmx | $2.67 | 18 KiB | 1,370 |
| Astro | $2.76 | 0 KiB | 1,461 |
| Nuxt | $2.82 | 84 KiB | 1,415 |
| Vanilla（Vite） | $2.98 | 7 KiB | 1,492 |
| Next.js | $3.14 | 142 KiB | 1,539 |
| SvelteKit | $4.28 | 36 KiB | 1,611 |
| Angular | $4.97 | 93 KiB | 2,009 |

*数据：Nolan Lawson，2026 年 10 月。成本是 Claude Code 按 API 价格折算的估计值，不是作者实际付出的订阅账单；代码行数为统计范围内的非空源代码行，不能直接解释为维护工作量。表格仅节选十二种技术栈。*

Hono + htmx 以 2.67 美元居首，Astro 只多出 9 美分。Next.js 的 3.14 美元也并没有与它拉开一个量级。更重要的是，各次运行的价格区间存在重叠：一次顺利的 Next.js 任务，完全可能比一次不顺利的 htmx 任务便宜。

所以，这些数字首先不是一张值得照抄的采购清单。

然而另一个差异很醒目：Hono + htmx 页面传送 18 KiB JavaScript，Next.js 则是 142 KiB；Astro 的这组实现甚至是 0 KiB。这些数字并不表示 Astro 或 htmx 天生优于 Next.js，而是表明：在这份偏重内容展示的任务里，Agent 为不同技术栈选择的实现方式，最终让用户下载了差异很大的脚本体积。

从程序员手里的代码，到真实访客手机上的字节，框架决策的成本并不只落在开发者身上。

## htmx 为什么会出现在第一名？

htmx 的做法有点像提醒 Web 开发者：浏览器原本就会处理链接、表单与服务器返回的 HTML，我们为什么总要先把这些能力拆掉，再用一套 JavaScript 程序重新组装？

给一个按钮加上 `hx-get` 和 `hx-target`，它就可以请求服务器返回的 HTML 片段，把结果放进指定的位置。复杂交互当然仍然需要设计，但很多列表、搜索和分页不必先变成一整套客户端状态管理问题。

Hono 则是轻量的服务端 Web 框架。两者放在一起，形成了一条比较直接的路线：服务器生成界面，浏览器负责显示与局部更新。

对这次图鉴应用来说，这条路线恰好够用。

但别误会：实验没有证明“HTML 属性比 JavaScript 更适合 AI”。作者自己也指出，这是一种偏内容、轻交互的应用，更接近维基百科，而不是 Gmail 或 Figma。如果需求换成离线协作、复杂画布、持续同步的应用内状态，客户端框架的价值可能迅速上升。

同样不能把移动端性能差异全算在框架头上。研究主要测量页面加载，没有充分比较页面加载后的交互；后端访问本地 API 也不受浏览器模拟慢网络的同等限制。服务端渲染、多页面应用在这种赛场上天然占了一些便宜。

htmx 赢的是这场比赛，而不是所有未来比赛。

## 真正的新成本，是机器理解系统的成本

文章最值得继续想的地方，其实还不在浏览器。

传统的开发者体验——Developer Experience，简称 DX——讨论的是人写代码的体验：文档好不好找，组件写起来顺不顺，工具链能不能让团队快速上手。

编程 Agent 加入以后，还需要问另一组问题：它为了理解框架要读多少资料？为了完成一项修改要打开多少文件？碰到陌生约定会不会走弯路？发现错误以后，要花多少额外调用才能修好？

实验里有一些有趣的现场。SvelteKit 的 Agent 在每次运行中都会阅读版本迁移指南；Gracile 的 Agent 有时需要查看框架源码。Hono 的官方 Skill 在全部五次运行中被用到，Nuxt 的 MCP 则一次也没被调用。作者甚至怀疑，某些面向 AI 的 MCP 和 Skill 可能没有产生预期的收益。

但这里不能倒过来推理，说“装了 Skill 就一定省钱”或者“框架越新越差”。工具是否被发现、是否被调用、调用后是否真的帮上忙，本身就是实验变量。

更复杂的代码也不一定更难维护。一套多写几百行、却明确规定边界与状态转换的系统，有时会比少写几百行、靠隐含约定串起来的系统更容易修改。Lawson 用非空源代码行数作为一个简便代理指标，是有启发性的；但它还不是一项长期维护实验。

**首次生成成本已经可以测量；持续迭代的理解成本、返工成本和回归风险，还需要下一场考试。**

## 当代码越来越便宜，什么才值得留下？

我们习惯把框架当作生产工具：一开始选对它，就能加快接下来几年的开发。

Agent 时代让这件事出现了微妙变化。某些抽象过去是为了让人少敲键盘而存在；如今机器很擅长敲键盘，我们得重新检查这些抽象还在替系统解决什么问题。

如果它帮助人和 Agent 都看清职责边界、避免重复实现、减少回归，那么它依然值得保留。如果它只是因为某个年代的技术潮流而被层层加上去，后来每次修改都得重新解释一遍，成本就不会随着 AI 变强而自动消失。

这和《见π》009 正在讨论的“维护”有一点相通，却不需要强行变成同一道题。

一个网站从生成出第一版页面，到三年以后仍然可读、能改、能迁移，之间隔着太多第一次跑分看不到的事情。真正需要比较的，也许不是“用哪个框架写第一版最便宜”，而是让同一位 Agent 连续完成十次有依赖关系的修改，再看测试、返工、性能和最终账单。

Lawson 的实验还没有给出这个答案。

它已经做成了一件更重要的事：**当编程方式变了，我们终于有理由重新拿起尺子，而不是继续用旧时代的手感替新选择辩护。**
