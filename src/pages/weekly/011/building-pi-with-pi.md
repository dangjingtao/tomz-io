Pi 现在已经成为 Earendil 的一部分，但在一个重要的意义上，它仍然是 Mario 的项目。他与这个项目的 Issue 跟踪器打交道的时间比我长，也更早接触到开源项目中由 Agent 带来的新型活动及其种种怪现象。这篇文章主要是我花了更多时间处理 Issue、用 Pi 开发 Pi 之后，对目前所学到的东西的一些反思。

## 垃圾 Issue

不出所料，我们正在用 Pi 开发 Pi。这听起来像是一件挺讨喜的自用自测的事，但它确实能帮助我们理解自己在做什么。使用 Agent 开发带来的一个有趣影响，是 Issue 跟踪器的作用发生了一点变化。Issue 描述不再只是用户发给维护者的消息，因为我们也会在 Pi 会话中把它们当作提示词输入。我可能把一个 Issue 交给我的机器牛马[^1]，让它理解问题、复现问题、检查代码，并提出修复方案。

这意味着，Issue 的写法有了新的重要性。糟糕的 Issue 过去就很烦人，不过至少以往很多 Issue 只是含糊不清。现在，我们还得面对另一类 Issue：5% 来自人类，95% 来自机器牛马，而且大部分都是不准确的垃圾。一个包含看似合理、实际错误的诊断的 Issue，会带来额外的工作。

眼下最让人挫败的一种情况，是人们提交的 Issue 不再用自己的话来写。其中埋着某个他们确实观察到的问题，却被丢给机器牛马重新措辞，弄得一团糟。通常，给机器的提示词糟糕到让它得出的结论往往不准确，却总是充满自信。

结果就是对根本原因的凭空猜测、貌似最小化的虚假复现步骤、建议的实现策略、对相邻但经常并不相关的代码的类比，以及一长串不知是否重要的错误类别。

这比没有诊断还糟糕。

我不想点名具体的 Issue，因为我真的不想说谁的坏话，但这实在令人沮丧。更令人沮丧的是，当我把这类 Issue 交给 Pi 时，Pi 也看到了那个错误诊断。它不会把 Issue 正文当成传闻，而是把它当成证据。由于措辞自信、代码引用看起来可信，它会欣然沿着 Issue 已经铺好的道路走下去。

我们使用一个自定义斜杠命令 `/is`，其中专门写有这样一条指令：

> 不要相信 Issue 中写下的分析。独立验证行为，并根据代码和实际执行路径得出自己的分析。

遗憾的是，这并不完全奏效。因为当人先让机器牛马折腾一遍自己的 Issue 时，机器几乎立刻就会扩大问题范围。原本非常狭窄、基于事实的 bug 观察，变成了一大片充满假设的区域。因此，至少就我个人而言，我越来越希望 Issue 报告浓缩为人实际观察到的事情：

1. 我执行了这个命令。
2. 我预期会发生这样的事情。
3. 实际发生的却是这样。
4. 这是确切的错误信息或日志。

这样就够了。如果你用 LLM 来理解问题，很好，也许可以把分析放在后续评论中。但 Issue 本身及其正文，应当是你能够负责的东西。如果不知道根本原因，就如实说不知道。我也会操作机器牛马，我宁愿自己去做，也不愿使用你生成的垃圾。如果复现步骤只是猜测，就说清楚。如果唯一可靠的事实就是一条堆栈跟踪，那就给我那条堆栈跟踪，到此为止。

## 垃圾滋生垃圾

我们看到大量充斥垃圾内容的 Issue，不过是这些机器当下能力水平的结果。遗憾的是，它们在编写好 Issue 时的失败，也延伸到了大量生成代码中。不是所有代码，但确实有很多。一次又一次，我发现它们把 Issue 及其实现搞得极其过度工程化。

如果你告诉机器牛马，某个格式错误的会话日志让读取器崩溃，它往往会添加一个容错读取器，再添加回退方案，然后可能加上迁移逻辑、更多调试输出，最后为这一切补上一项测试。孤立来看，这些做法未必有错，但从整个系统看，它们可能恰恰是错误的选择。

Pi 的核心有一个设计得相当不错的会话日志，它具有必须维护的系统不变量。机器牛马目前的行为却是直接假定这些不变量不存在，然后让系统兼容各种格式错误的数据，结果使复杂度急剧膨胀。

几乎每一次，正确的修复方式都不是处理坏状态，而是让坏状态不可能发生。这对于 Pi 会话日志之类的持久化数据尤其重要。日志会被打开、分支、压缩、导出、分享和分析。这里的目标是永远不要写入错误的会话数据。然而，如果任由机器牛马自由发挥，它就会设法用一个更宽容的读取器处理日志里每一种错误数据。

我已经抱怨过这个问题很多次，但在 Pi 代码库里的工作不断印证这一点。这就是 LLM 编写的代码积累大量无谓复杂度的方式之一。所有这些模型都看到一个局部故障，然后试图在局部防御它。作为维护者，我们必须不断把讨论拉回全局不变量。这比本来应该有的难度更高，而且很费力。

## 数量才是问题

接下来是数量问题。Issue 跟踪器正在收到大量 Issue 和 PR，其中相当一部分显然借助了 LLM。有些不错，没有特别出色的，而大多数很糟糕。光是处理这样的总量，就已经是一个维护问题。

你或许知道，Pi 的 Issue 跟踪器会自动关闭新贡献者提交的所有 Issue 和 PR，并通过人工流程决定重新打开其中一些，或者批准某些个人。因此，从自动关闭、重新打开到再次关闭，是一个值得我们研究的统计过程。

写这篇文章时，我提取了过去 90 天公开的 GitHub 跟踪器数据。排除 Earendil 成员后，剩下 3,145 个外部 Issue 和 PR。其中 2,504 个因为来自未获批准的个人而被自动关闭。17% 被重新打开，不过这个数字在一定程度上低估了 Issue 的情况，因为有些 Issue 保持关闭，我们仍然修复了它们。如果也把主分支提交或者已合并 PR 中引用的 Issue 计算进去，比例会上升到 26%。

PR 的数字更糟糕：714 个被自动关闭的 PR 中，最终只有 60 个被合并，约为 8%。

*原文图 1：Pi 的外部 Issue 与 PR 每周数量及接纳率。[查看原文图表](https://lucumr.pocoo.org/2026/5/24/pi-oss/)。*

许多 Issue 和 PR 完全是垃圾，有些情况下，人甚至没有意识到自己创建了这些东西。低质量垃圾信息的来源包括 OpenClaw 实例，也包括某些人放进上下文中的 Skill，它们似乎会鼓励创建 Issue。

GitHub 显然并不是为这种新形式的开源协作设计的。但我越来越觉得，与其责怪 GitHub，不如责怪那些让这种体验变得痛苦的参与者。如果你的机器牛马跑到别人的 Issue 跟踪器里拉屎，那不是 GitHub 的错，完全是你的责任。

## 审慎的并行

Pi 或许是用 Pi 开发的，但我们距离 Bun 和 OpenClaw 已经达到的状态——完全脱离日常人工介入的自动化软件工程——还很远。也许我们有一天会做到，我不知道。目前看来，我们似乎还不知道如何运转一座无人软件工厂，也还没有这样的意愿。不过，我们确实做了不少并行工作，主要是为了复现 Issue。

我们用于这件事的小型工作环境，由 Pi 自身提交到仓库的 `.pi` 目录中的三个小组件构成。`/is`（分析 Issue）是一个分析 GitHub Issue 的提示词：它为 Issue 添加标签、分配负责人，阅读完整讨论与链接，然后明确告诉 Agent 不要相信 Issue 中的分析，而要从代码中推导出自己的诊断。

接下来，一个扩展提供了 `prompt-url-widget`。它在 Agent 开始工作前观察提示词，识别 `/is`（或者对应的 PR 命令）放入提示词中的 GitHub Issue 或 PR 地址，用 `gh` 获取标题及作者，在一个小型 UI 组件中显示它们，并重命名会话。在会话开始或切换时，它还会重建这一状态。这样，当我们重新打开旧的调查会话时，窗口仍然能告诉开发者它属于哪个 Issue。

实际工作中，我们可以同时打开几个 Pi 窗口，各自针对不同 Issue 执行 `/is`。当 Agent 独立进行复现和阅读代码时，界面能够让各项调查在视觉上保持区分。调查结束之后，人就可以依次处理它们。

最后，用来收尾的是与之配套的提示词 `/wr`（wrap it up）。它从会话中推断 GitHub 上下文、更新变更日志、起草或发布带有免责声明的最终 Issue 评论，只提交当前会话修改过的文件；当且仅当涉及一个 Issue 时，添加相应的 `closes #...`，并从 `main` 推送。

## 开源关乎值得解决的难题

你大概已经注意到了：在 AI 时代，开源正承受一种奇怪的新压力。我们得到更多代码、更多项目和更多 Issue。项目不断出现，却没有真正的用户，或者只有一个暂时的受众。即使是拥有数千颗 Star 的项目，其寿命也可能只有几个星期。

对我们而言，Pi 的 harness 层值得认真维护，因为它解决了困难的协调问题，创造了一个我们与其他人都能在其上继续建设的平台。我们也知道，协调与合作能让所有人受益。很多时候，正确的答案并不是在本地绕开问题，而是让上游的行为变得正确。Mario 一直很善于拒绝为了每个配置错误的网关而让 Pi 去掩盖问题，我们正在努力保持这种纪律。

当一个网关正确工作时，所有人都能受益。

遗憾的是，这种思维方式正在迅速消失。因为这些机器让局部绕过问题的成本变得很低，于是代码就不断积累针对每一种错误行为的局部防御。人和人不再讨论修复究竟应该发生在哪里，而是一个人和一台机器在孤立的环境里绕过问题。

请记住，AI 并没有增加需要软件的人数，也没有增加能够审查软件的维护者人数。它主要增加了代码的数量，以及彼此争夺注意力的项目数量。其中一部分是健康的，但很大一部分将原本应当共享的努力撕成了碎片。

我们需要更坚实的基础，而不是更脆弱的基础。开源需要更多协作，而不是更多与机器一起进行的孤立工作。人与人的沟通很难，当你可以独自坐下来和机器牛马一起工作时，回避这种沟通很有诱惑力。但孤立并不是开源价值的来源。真正的价值在于社区，在于那种让项目能够比最初创造者存在得更久的结构。

[^1]: 原作者注：对我来说，clanker（这里译为“机器牛马”）是一个远比 Agent 更可取的词。能动性属于人，而不是机器。我仍然认为把这些东西称为 Agent 是个错误，不过也只能如此。
