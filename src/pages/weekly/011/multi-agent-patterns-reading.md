# 多智能体系统的三种架构：从选型到可靠交付

**评论对象作者：Kadharmoideen Fadurudeen**  
**原文：[Building a Multi-Agent System: 3 Patterns, Explained Simply](https://kadhar.dev/blog/multi-agent-systems-from-scratch)**  
**原文发表：2026 年 6 月 8 日**  
**本文性质：《见π》知识导读与独立工程评论，非原文翻译。**

*不要用组织架构掩盖工程问题。*

一名开发者做出一个能推荐晚餐的 AI 助手。它使用少量工具，工作正常，最终却因为 API 支出而停止运营。

这是 Kadharmoideen Fadurudeen 的文章里最应该被读到的一件事。系统没有陷入无限循环，也没有表现出什么惊人的智能失控。它只是在有限预算下不能持续经营。

多 Agent 系统的第一性问题不是组织多少个智能体，而是如何在给定的资源约束下交付可靠结果。

## 一、什么才算多智能体系统？

Kadhar 在原文介绍了 Pipeline（流水线）、Orchestrator（协调者）和 Blackboard（黑板）三种模式，强调先验证单 Agent 是否已经足够，并将数据校验、资源限制和评估放在模型控制之外。[原文的交互演示](https://kadhar.dev/blog/multi-agent-systems-from-scratch) 是一个脚本模拟器，并非实时运行的 AI 系统。

下面以《见π》的编辑工作作为统一的教学案例。架构示意、数据契约、选型比较与工程推演均为本文自行构造，并不表示《见π》当前系统采用了这些实现。

设想我们需要交付一篇有关开放硬件的科技报道。工作包括寻找项目资料、核对事实、组织文章，并在人工审核后形成可出版稿件。

如果一个 Agent 已经可以调用网络搜索、正文读取和草稿写入工具，并且能够在预算内完成，最简单的架构就是：

![单 Agent 基线：工具是操作接口，决策循环仍只有一个。](/images/weekly/011/single-agent.svg)

*单 Agent 基线：工具是操作接口，决策循环仍只有一个。 制图：《见π》。*

拥有三个工具不等于拥有三个 Agent。工具承担具体操作，Agent 决定何时进行操作、如何依据结果安排下一步。程序同样可以包含多个模块，而只有一个模型决策循环。只有将部分决策委托给另一个具有独立上下文与任务边界的模型执行单元，才产生这里讨论的多 Agent 协作问题。不同 Agent 可以使用同一个模型，并不要求每个角色都有不同的基础模型。

在设计前，先辨别需要的究竟是独立推理、并行处理、权限隔离，还是普通的数据处理函数。如果只是读取 JSON、判断日期或限制请求次数，通常不需要再设立一个会思考的角色。

## 二、Pipeline：固定工序的流水线

流水线把任务变成一系列有方向的处理阶段。每一步的输出成为下一步的输入；调度程序决定阶段的顺序。

![流水线：固定工序、程序校验、有限返工。](/images/weekly/011/pipeline.svg)

*流水线：固定工序、程序校验、有限返工。 制图：《见π》。*

### 怎样运行

研究阶段只负责获得证据，不直接宣布出版；成文阶段依据已校验的材料写作，不自行将假设升级为事实。程序负责判断来源地址、必填字段和引用结构是否符合约定。最后由有出版权限的人决定稿件是否接受。

流程、分支及返工条件可以由普通代码或状态机表达，不一定需要一个负责分派任务的模型。

### 何时适合

流程能够事先描述，阶段之间有自然依赖，输入输出边界清楚。例如发票提取后生成账目、将研究材料编成报道、按明确测试契约交付一个小型功能。

在这种结构里，能够独立测试某个阶段，是比“角色分工看起来专业”更重要的优势。我们可以用固定证据清单测试成文阶段，而不用在每次测试时重新执行网络搜索。

### 怎样失败

如果审核发现原始论文没有覆盖文章声称的结论，问题发生在证据不足，而不是措辞。让成文 Agent 一遍遍润色没有价值。

流水线可以接受有限返工，并不意味着必须绝对直线运行。但如果流程中不断出现事先无法枚举的跨阶段依赖，固定编排就容易积累越来越多的特例。此时应该重新判断问题是否属于另一种模式，而不是无限添加跳转。

## 三、Orchestrator：一个负责人，多个独立的施工者

协调者负责理解目标、分拆任务并综合结果；工作 Agent 在各自的范围内执行。此处讨论的是中心辐射式结构：工作 Agent 的信息经协调者汇合，而不是任意彼此派工。

![协调者：动态委托、并行调查与集中交付。](/images/weekly/011/orchestrator.svg)

*协调者：动态委托、并行调查与集中交付。 制图：《见π》。*

### 怎样运行

对于开放硬件报道，主编可能先启动三项互不依赖的研究：开发者经历与技术实现、制造服务及成本、实际测试与交付证据。它们可以并行推进，但并行是否有效取决于真实依赖、工具限额与共享资源，而不是图上画了多少个工作 Agent。

资料返回后，主编可能发现制造报价没有包含封装与测试费用，从而追加一个精确的调查任务。与流水线相比，差别不只是并行，而是下一轮任务由负责人依据中间结果动态决定。

### 何时适合

目标明确、能够识别不同专业方向，但调查步骤和必要的工作量无法提前确定。例如开放式调研报告、多模块改造、跨源资料核验。

协调者应持有任务分派、依赖关系和完成条件。工作 Agent 应携带足够的上下文，但不必获得全部会话历史、修改权限或其他任务的秘密。一个轻量的确定性调度器也可以承担运行管理，让模型只处理需要判断的地方。

### 怎样失败

如果主编把问题定义错了，例如将一次受赞助的流片错误理解为已经有市场售价，所有工作者可能在错误前提下同时寻找支持材料。并行并没有减少这种系统性错误。

另一个问题是协调者变成吞吐瓶颈。工作 Agent 产生的长报告全部进入它的上下文，综合所需的 token 与人工验收成本可能抵消并行收益。

因此，应明确由谁决定补查、谁有权停止、谁对最终交付负责。工作 Agent 的成功不能直接代替最终任务的成功。

## 四、Blackboard：围绕同一事实空间探索

黑板模式不依赖一个模型持续指定每一步。各个工作单元通过共享的状态交换知识，根据当前可用证据判断自己是否能够提供新贡献。这种架构的调度和终止仍可以由确定性程序负责。

![黑板：多个工作单元读写共享事实，由程序约束状态和终止条件。](/images/weekly/011/blackboard.svg)

*黑板：多个工作单元读写共享事实，由程序约束状态和终止条件。 制图：《见π》。*

### 怎样运行

假设编辑发现作者声称一颗芯片已经制造出来，却没有提供测试结果。

一个工作者在共享空间提出假设：芯片可能已经完成制造，但尚未完成电气验证。另一个工作者去找作者的后续日志和项目仓库，发现有裸片照片，却没有测试记录。第三个工作者指出，照片无法证明封装、电气或网络功能已经实现。

这些证据会改变接下来的工作：也许应继续调查测试板进展，也许应该停止调查，直接把“功能未经验证”标记为不可确认的事实边界。没有必要在发出任务时就写好完整步骤。

### 何时适合

需要随着新发现不断改变调查方向的问题。例如复现难以定位的故障、分析相互冲突的证据、探索缺乏完整规格的设计。

共享黑板不等于所有人向同一个群聊发消息。真正有用的是可读取、可更新、可追踪的状态，而不只是持续增长的对话记录。可以让假设具有唯一标识，证据具有来源，工作项具有负责人，已被证伪的假设保留结论而不是重新进入待办。

### 怎样失败

如果没有明确的停止机制，研究者可能提出一条新假设，反驳者要求补证，研究者又提出另一条相似假设。所有参与者都在合理工作，整个系统却没有向目标收敛。

并发写入还可能产生互相覆盖。某个结论已被证伪，另一个使用旧状态的 Agent 却可能再次宣布它成立。实际实现需要版本号、原子更新、重复任务检测以及冲突处理规则。缺少这些能力时，不应把共享聊天历史冒充可靠的黑板。

## 五、怎样选结构：从控制流，而不是从人数出发

| 维度 | 流水线 | 协调者 | 黑板 |
| --- | --- | --- | --- |
| 控制权 | 预定义的流程 | 动态决策的负责人 | 共享状态及调度规则 |
| 工作顺序 | 大体预先确定 | 随任务分解改变 | 随证据进展改变 |
| 信息交换 | 工序间交接 | 工作单元与负责人 | 读写共享状态 |
| 并行条件 | 无依赖的阶段或分支 | 无依赖的委托任务 | 可并发更新的独立工作 |
| 测试重点 | 工序输入输出和异常分支 | 分派、综合及全局完成条件 | 状态一致性、冲突和收敛 |
| 主要风险 | 刚性和错误累积 | 中心判断错误、上下文压力 | 循环、冲突与不收敛 |

这张表不是一份架构性能排名。对于相同的需求，不同实现的速度和成本必须通过实验比较。一个常见的混合策略，是用流水线管理整个交付过程，在研究阶段内采用协调者并行调查，只在遇到无法预知的故障时开启受控的探索空间。

### 一个微型成本实验

假设一篇报告需要三项相互独立的调查，每项模型工作用时 20 秒，汇总需要 10 秒。暂不考虑网络限流、调度开销、失败重试和模型资源竞争：

| 实现 | 理想墙钟时间 | 调查及汇总的模型工作量 |
| --- | ---: | ---: |
| 三项依次执行 | 70 秒 | 70 模型工作秒 |
| 三项完全并行 | 30 秒 | 70 模型工作秒 |

这里只是教学假设，不是任何框架的真实基准。并行缩短的是等待时间；上下文重复、额外协调及返工甚至可能增加计费 token。模型工作秒也不能直接换算成 API 价格。

对一个需要长时间等待的研究任务，较高的并行度可能有价值；对只有几步的即时请求，它未必能补偿启动、交接和汇总成本。

### 四个最小控制条件

无论选哪种模式，系统都需要回答四个问题：状态是否可信，资源是否有上限，交付如何判定，失败如何结束。

例如，可以为每项编辑任务定义下列状态，这是一份简化的独立设计示例：

~~~json
{
  "task_id": "editorial-001",
  "status": "needs_evidence",
  "claim_id": "chip-functional-test",
  "evidence_ids": [],
  "remaining_steps": 2,
  "next_action": "request_source_or_stop"
}
~~~

当证据为空时，程序可以禁止这条事实进入已核实结论；当剩余步骤用尽时，只允许输出部分成果或转交人工。日志需要记录每次转移的原因和引用的证据，而非只保留最终文章。

三种架构解释的是工作怎样组织，工程控制解释的是工作能否可靠完成。这是两个互补的设计层。

## 六、我们究竟要拆什么？

Kadhar 讨论了三类架构：串行流水线、中心协调和共享黑板。但这些形式本身并不是需求。

可以先建立一个容易被忽视的区别：**拆分程序职责与拆分模型的自主决策，不是同一件事情。**

查询数据库、解析字段、淘汰过期数据、计算余额和限制调用次数，大量工作都能交给确定性程序。将这些步骤包装为具有自主判断能力的 Agent，并不会自然增加它们的价值。

| 问题 | 优先尝试 | 什么时候值得引入新的 Agent |
| --- | --- | --- |
| 数据读取或转换 | 普通函数、结构化工具 | 输入高度非结构化且规则覆盖不足 |
| 多项独立调研 | 并行工具调用 | 子任务需要独立推理空间或较长上下文 |
| 成果综合 | 单一负责者 | 不同专业判断需要独立探索 |
| 质量验收 | 可重复运行的测试 | 需要判断难以形式化的体验和语义 |

这张表是《见π》提出的决策框架，不是作者的原表。它试图避免一个成本很高的设计习惯：先定义一群角色，再给每个角色寻找事情做。

应当先确认单 Agent 基线，再看新的决策单元是否确实降低了错误率、耗时或维护负担。没有基线，就无法证明拆分是进步。

## 七、一个天气助手的实验，比架构图更重要

Kadhar 的另一项工作 Stormwise 提供了可检验的证据。其 11 月 3 日发布的 arXiv 预印本，使用美国国家气象局历史警报构建固定测试集，考察模型在危险天气中给出虚假安慰的情况。

研究有 117 个案例，包含 69 个有警报案例、32 个无警报对照案例及 16 个美国以外地区案例。针对有警报案例，作者人工标注了 342 条回答，并报告以下结果：

| 实验条件 | 虚假安慰 | 比例 |
| --- | ---: | ---: |
| 无真实警报数据，普通提示词 | 26/69 | 37.7% |
| 无真实警报数据，要求披露信息缺失 | 31/69 | 44.9% |
| 接入真实警报，普通提示词 | 0/69 | 0% |
| 正式系统配置 | 0/66 | 0% |

资料：[False Reassurance in LLM Severe-Weather Guidance（arXiv:2611.05290）](https://arxiv.org/abs/2611.05290)。

这项实验最直观的启示是：一个被要求坦诚的模型，仍可能无法弥补它所不知道的事实。数据的可用性与质量，是系统能力的一部分。

但还有一个不应漏掉的反例。仅接入警报数据、使用普通提示词的配置，在无警报对照案例中出现某种程度警示的比例达到 87.5%；正式配置则为零。换言之，减少危险场景中的虚假安慰，并不自动等于整个系统变得可靠。还要看它是否能在无危险时保持准确。

零次错误也不是未来零风险的证明。正式配置的 0/66 对应论文报告的 95% 置信区间上界为 5.5%。这项工作仍是预印本，人工标注由一名评审者完成，实验场景也有地域及样本范围限制。不能直接推广为所有气象场景或所有模型的有效性结论。

## 八、把智能体交接看成数据边界

当一个 Agent 将自然语言结果传递给另一个 Agent 时，原来的不确定性很容易在传输中丢失。

假设数据收集者说某个版本可能存在漏洞，协调者把它总结成了确认存在漏洞，执行者便可能开始修改代码。这里没有必要假设某个模型笨得离谱：三次各自合理的推断，就足以形成一个错误的工程行动。

与其让每次传递都依赖另一段提示词，不如明确交接合同。例如，一次调查结果至少应能区分：

- 原始证据与获取时间。
- 已验证事实、假设及缺失信息。
- 允许下一环节执行的动作和验收条件。
- 调查失败或证据不足时的终止状态。

关键字段应由程序检查，而不是只由下一位模型判断。数据库可以拒绝非法状态，权限层可以拦截未经授权的操作，时间戳可以检查数据新鲜度。这些普通的软件能力并不因为系统中加入了 AI 而变得过时。

## 九、把预算和验收放到智能体外面

Stormwise 的实验还推翻了另一种直觉：自动评分器不一定是可信的裁判。作者最初的正则检测漏掉 57 个真实错误中的 53 个，甚至导向了相反结论。

因此，评价一个评审 Agent 时，也需要准备独立的标注集，分别观察漏检与误判。不能用一个模型认可另一个模型的输出，就宣告质量闭环。

这同样适用于预算。可以把一次任务的总成本理解为模型推理、外部工具、失败重试及人工验收成本的组合。一个单独设置的 Agent 限额不能代表整个请求存在全局上限：当上下游互相请求帮助、重试或返工时，各自守规矩的节点仍然可能组成昂贵的系统。

我建议先确立三个对任务全局生效的约束：总资源预算、可追踪的状态迁移以及明确的失败出口。

超出预算不应该被解释为任务已完成。系统应说明已经取得的证据、尚未完成的部分，以及是否需要人类作出进一步决定。一个能如实结束的失败，比一个把不完整结果包装成成功的系统更有价值。

## 十、哪种结构最适合真实团队？

对于固定流程，流水线的价值在于每个工序可以独立验证，但它不应该强制把所有例外倒回同一条线路。对于需要动态委托的研究或施工任务，协调者应对依赖与最终交付有清晰责任，而不是仅充当消息转发器。对于探索性问题，共享工作空间可以保留多条思路，但需要证据版本、写入控制及结束条件。

它们可以组合：例如一个确定性调度器启动独立调查，汇总后交给负责者作判断；只有确实需要探索的局部才开放多轮交互。

《见π》更愿意用以下成功标准验收这类系统：在相同任务和预算下，比较单 Agent 与多 Agent 的实际交付成功率、人工干预时间、失败恢复及真实总成本。并行快了多少、返工多了多少、错误是否更容易定位，都应由真实记录回答。

如果增加五个 Agent 后，人必须多开五个窗口理解五份进度，还需要替它们弥补错误，那些被转移出去的工作可能会以另一种方式回到人的身上。

不要把角色图画得越来越像公司，却忘了我们最初使用 AI 是为了减少工作的负担。
