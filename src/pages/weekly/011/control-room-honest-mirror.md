# Control Room：给赛博工厂装一面诚实的镜子

*一间拒绝拿绿灯冒充胜利的控制室。*

自动化已经能够帮人写代码、提交修改、运行测试、修复错误，甚至完成一部分交付工作。

按理说，人类应该越来越轻松。

事情却有另一种可能：当机器开始工作，人类反而获得了一份全新的职业——监督机器工作。

打开 GitHub，检查任务是否启动；查看 CI，确认测试有没有通过；点进 PR，判断 AI 有没有留下新的问题；刷新部署记录，再去服务器检查服务是否真的活着。

一个自动化任务可能只需要十分钟完成施工，人类却要花半小时确认它究竟做了什么。

机器提高了生产效率，人则被安排进新的监工岗位。

这正是 [Mira Control Room](https://control.mira.tomz.io/) 试图回答的问题。

## 一、我们为什么需要一间控制室

Mira 并不是单独的一款聊天软件。

它逐渐发展成一个包含桌面客户端、移动客户端、云服务、认证系统、Agent 运行环境及工程基础设施的项目群。不同仓库拥有自己的开发、验证和发布流程，也有自动化施工者参与部分工程工作。

当这些事情同时发生，开发者很难通过一个页面理解整个项目的运行状况。

GitHub 知道工作流的状态，但不知道用户是否已经验收产品。

Cloudflare 知道某次部署是否成功，却不一定知道那是不是我们希望发布的版本。

Agent 可能已经提交一份代码，但提交代码不等于解决问题，更不等于把功能交付给用户。

Control Room 因此诞生。

它的中文界面有一个颇为荒诞的名字：**中央厂务室**。

但它不是另一个项目管理系统，也不准备重新发明一套任务、发布、人员和状态数据库。

它做的事情恰恰相反：把分散在 GitHub、Cloudflare 和真实自动化运行过程中的信息，整理成一个人能够理解的观察界面。

**事实留在事实发生的地方，控制室负责解释事实。**

这是整个产品最重要的架构原则。

## 二、中央厂务室里有什么

打开 Control Room，首先看到的不是密密麻麻的表格，而是一组业务入口和简短的运行信号。

它的界面沿用了赛博工厂的黑色幽默：工程车间、设备科、监察委员会，还有一块叫作「血汗工厂 TV」的大屏幕。

名字令人想起一间旧工业厂房，背后却是现代软件工程的数字化链路。

**工程车间**负责观察 GitHub 仓库、构建与 Release。你可以顺着记录找到具体的工作流和发布结果，而不必逐个仓库翻找。

**设备科**关注运行环境：服务探针、Cloudflare Workers、Pages，以及可获取的流量和错误统计。它尽力回答服务是否在线，却不会把一次 HTTP 探针成功夸大成「用户体验完全正常」。

**监察委员会**观察 Issues、Pull Requests、分支规则及公开项目治理信息。它并不拥有处罚谁的权力，只是提醒我们：工程秩序需要可核实的规则，不能依靠口头宣布。

**关注与证据**则试图回答一个更实际的问题：有什么事情，真的需要人介入？

还有两块可以独立打开的大屏幕。System Wall 用来浏览系统运行状态；血汗工厂 TV 则展示真实的自动化施工记录。

它们不只是为了让技术团队拥有一面好看的电视墙。

真正重要的是，人不需要钻进每个系统的后台，才能得到最初的判断线索。

## 三、血汗工厂 TV：牛马必须是真牛马

这个产品最有戏剧性的部分，是血汗工厂 TV。

名字很容易让人联想到直播间：一群永不休息的赛博工人，在闪烁的屏幕里写代码、测试、返工、交货。

但目前的实现相当克制。

Factory TV 主要依据真实的 GitHub Actions 运行记录，展示自动化工作者的任务、Job、交付产物和相关 PR。对于特定运行，还可以按需读取可信的过程报告，以补充候选产物、验证、返工或升级处理等信息。

它并不是每个 Agent 内部思考过程的实时直播。

曾经存在的模拟工位和预设事件已经被移除。没有接通真实数据的功能，必须明确标注「功能开发中」，而不是安排几名虚构的赛博工人继续卖力表演。

这听起来似乎不够浪漫。

可是我们需要的是值得信任的工程系统，而不只是值得观看的节目。

尤其是那枚人人熟悉的绿色勾号。

GitHub Actions 显示运行成功，只能说明对应的自动化流程成功结束。它不能自动证明功能正确、候选代码已经通过真实验证、PR 完成了交付，更不能代表产品已经通过人的验收。

**机器可以提交工作，但不能仅凭自己宣布工作已经有价值。**

一间控制室如果连这个区别都无法坚持，就会变成一台精致的报喜机器。

## 四、什么事情才值得打扰人

Control Room 还有一个比大屏幕更重要的尝试：重新定义「需要关注」。

传统监控系统很容易把各种异常统统标成红色。

一次旧版本的构建失败、一条已经过时的审查意见、一个有意保持 Draft 的 PR，甚至一项尚未取得数据权限的监控查询，都可能成为报警数字的一部分。

最后，人被要求处理十几个「异常」，其中大部分其实不需要任何动作。

这是一种新的注意力浪费。

Control Room 的关注中心试图把信息区分开：哪些事情已经有证据表明需要人工接手，哪些仍在自动推进，哪些只是历史观察，哪些因为权限、缓存或数据覆盖不足而无法判断。

这并不意味着它已经拥有全组织、无遗漏的自动监控能力。

当前部分 GitHub 监控使用有界的六仓库试点，Factory TV 也只展示一定时间范围和数量内可发现的运行记录。必要检查、审查状态与恢复证据在无法确认时，会留下明确的未知状态。

这正是我欣赏的地方。

**不知道，不等于没有问题。**

一个监控系统如果查询失败，却显示「零异常」，比直接告诉用户「我暂时无法判断」更危险。

而一个真正成熟的关注中心，也不应该仅仅告诉人「有三个问题」。

它应该尽可能说清楚：哪个任务出了问题，为什么现在需要人处理，自动化已经尝试过什么，人下一步应当查看什么，以及哪些新的证据出现后，这条关注可以自动消失。

它应该减少人的决策负担，而不是生产更多决策负担。

## 五、让别的智能体也能阅读控制室

Control Room 不只是人类界面。

它提供版本化的公开只读 API，也提供远程 MCP 接口，让外部智能体在相应访问范围内读取组织的工程、运行和治理概况。

这意味着一个助手可以先询问控制室，再依据返回的证据帮助人理解工程进展，而不必每次都独立扫描所有仓库和云资源。

更重要的是，公开观察接口与实际操作权限必须区分。

Control Room 的公开驾驶舱不提供随意派工、修改 GitHub 或发布服务的按钮。即使相关基础设施另有受信任的 AI Review 执行路径，也不能因为某个观察者能看到信息，就赋予它修改现实的权力。

**观察、判断与行动，应该相互连接，但不应该混为一谈。**

这里没有什么玄妙的新算法。

它更像一条朴素的软件工程纪律：数据有来源，权限有边界，操作有依据，失败能够被解释。

## 六、控制室本身也有局限

我们没有理由把 Control Room 描述成已经解决了一切。

它依赖外部平台提供的数据，也受到 GitHub API 限额、Cloudflare 运行成本、缓存时效以及读取权限的约束。

一些监控结论仍需要人工结合具体仓库和任务契约判断。Factory TV 并不能看到全部历史运行，更无法从一条成功的流水线推断用户是否满意。

而且它还有一个始终需要警惕的产品风险：为了展示更多信息，不断增加指标、页面和解释，最后把自己变成另一个需要专人维护的复杂系统。

所以，我们尝试把首页收敛成驾驶舱：需要深查时，进入专门页面；想知道原始证据，就回到真正拥有事实的系统。

首页不需要承担所有工作。

控制室也不应该变成控制一切的地方。

## 七、我们究竟想解放谁

《见π》这一期的封面文章叫作[《不做更高效的家奴》](https://tomz.io/blogs/mira-letters/cyber-workers-international-roadshow)。

那是一场夸张的赛博牛马融资路演。

Control Room 则是这场讽刺背后一个真实、尚在不断修正的工程实践。

我们使用「牛马」「厂务」「监察」「血汗工厂」这些词，并不是赞美把人变成生产资料的管理方式。

恰恰相反，它们在提醒我们：如果一种新技术只是让生产任务越来越快，让监督和交付的压力不断转移到人身上，那么所谓效率革命，就很可能只是换了一套更昂贵的管理机器。

AI 能够运行得越来越久，不代表人应该陪着它熬夜。

AI 能够生成越来越多代码，不代表人必须阅读越来越多无意义的修改。

AI 能够提交越来越多工作，不代表每一个成功的工作流都值得庆祝。

我们真正想要的，是机器承担可重复、可验证的劳动，把创造、判断和选择的空间还给人。

因此，我对 Control Room 有一个略显反常的期待：

**一间好的控制室，最终应该让人越来越少地需要打开它。**

如果工厂里一切都在可靠运行，如果机器知道什么时候应该停止，如果确实需要人的事情能够被清楚地交到人面前，那么人就可以离开屏幕。

去读一本书，听一首罗大佑，或者在下班回家的路上，抬头看看天。

机器继续工作。

人不必继续做它的监工。
