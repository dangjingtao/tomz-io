# 不再逐行阅读代码之后，我们如何相信软件？

2026 年 9 月 19 日，软件工程师、Amp 联合创始人 Thorsten Ball 把此前在 X 上引发讨论的一组观点放进个人博客。他说，代码审查将死，单元测试也许会死；写代码的技艺会消失，终端会退场，产品经理、设计师与工程师之间那套熟悉的分工终将瓦解。全文一共十六条判断，读起来像一份刻意不留退路的宣言。

他又不是一个旁观编程多年、终于找到机会宣布程序员过时的人。Ball 写过 Go 语言解释器和编译器的书，也长期在开发者工具行业工作。正因为如此，他对终端、开源和代码本身所说的那些话，比普通的“AI 将改变编程”更值得认真读。

但这些句子容易让讨论走偏。支持者忙着宣布旧时代结束，反对者则只要指出某一条还没发生，似乎就可以把整篇文章驳回。对一篇试图描述长期变迁的文章，这两种读法都太便宜了。

我们不妨先放下“谁会死”的修辞，问一件更难的事：**如果未来的软件确实大部分由模型生成，人类不再逐行检查它，那么我们凭什么相信它能工作，而且能持续工作？**

## 一、他真正切开的，是两种原本被混在一起的能力

Ball 同时说了两件看似矛盾的事：写代码越来越不重要，构建软件却越来越重要。

我们太容易把两者当成同一件事了。过去，一个人能够写出可靠程序，往往也意味着他理解系统约束，能把需求翻译成实现，能处理交付中的种种摩擦。代码是最终产物，也是衡量能力的主要可见证据。因此，当模型能够迅速生成一份几百行、几千行的实现时，我们习惯性地问：“那程序员还要做什么？”

Ball 的答案实际上并不是“什么都不用做”。他说，知道如何用软件解决业务问题，知道别人为什么这样做、什么时候应该交付、如何取得反馈，这些能力会变得更重要。

这个区分很关键。**源代码的生产成本降低，并不自动降低正确选择问题的难度。** 模型可以在几分钟内实现一个漂亮的报表界面，却无法仅凭“做一个报表”的指令判断使用者究竟需要监控异常、解释预算，还是向上级汇报一个已经被决定的结论。同样一句需求，可能通向三个完全不同的产品。

所以他还有一句更值得反复咀嚼的判断：未来很多错误不再是代码写错，而是人提出了错误的问题。

当然，这并不意味着代码错误会消失。安全漏洞、并发条件、权限越界、数据迁移、第三方系统异常，都可能继续以很传统的形式出现。Ball 描述的是**错误重心的迁移**，不是提出一个可以直接拿来代替测试的定理。

## 二、九百行 Arduino C，不能直接推导出单元测试的死亡

Ball 举了自己的一个例子：模型写出约九百行 Arduino C 代码，一次编译成功，烧录到设备上也运行得很好。他以此追问，当模型能稳定写出大量正确代码，为什么还需要单元测试这种“辅助轮”？

这个故事说明模型已经能跨越一段此前需要开发者手工处理的距离。但它并不能单独说明，在更复杂的系统里，我们不再需要独立检查。

一次运行成功与长期可靠之间，还隔着很多东西：不同输入、不同状态、版本升级、错误恢复、设备差异、未预见的负载，以及用户真正会采取而开发者未曾设计的操作。九百行代码一次跑通可以是很好的能力展示，却不是一个有统计意义的可靠性结论。

这里还存在一个更有意思的反转。**代码越便宜，验证就越不能继续依赖人工手工完成。** 如果模型能在几分钟内改写整个模块，却要求一个工程师花两天逐行阅读，那么被自动化的只是一半工作。更合理的方向，是让自动化验证能力随自动化生产一起增长。

这并不是在为传统单元测试的每一种习惯辩护。为了覆盖率而写出的琐碎测试、重复实现细节的断言、与真实用户行为脱节的 Mock，确实可能在新工作流里越来越不划算。值得保留的，是能在错误被交付之前证明它存在、并且能让问题被复现的检查。

换句话说，单元测试的地位可以下降，某些形式甚至可以被淘汰；**验证这个动作本身却没有因此失去必要性。**

## 三、比宣言更有说服力的，是 Ball 自己实际怎么做

十月十三日，Ball 在 Amp 的公开工作录像中展示了自己如何让 Agent 完成任务。他不再依靠传统的本地编码过程，也不习惯逐行读完模型提交的全部代码；对重要文件和关键设计，他仍会检查。更重要的是，他要求 Agent 提供端到端运行证据、测试记录与可观察的结果。

在 [Amp 的工作方式访谈](https://ampcode.com/docs/using-amp/thorsten) 里，他还谈到用 Feature Flag 控制新功能：先让变更在生产环境中隔离上线，再由自己试用，之后逐步扩大范围。他会让 Agent 观察部署和流量，也会要求它们检查生产环境的性能变化。

这恰好是理解他那句“代码审查已死”的钥匙。Ball 实际丢弃的，更多是**把人类逐行阅读 PR Diff 当作默认验收方式**。他并没有让软件在完全缺少证据的情况下自行进入世界。相反，他试图把证据收集、运行验证、灰度放量与回滚能力都移到 Agent 能操作的系统里。

这种方法很有吸引力，但它成立需要条件。团队必须掌握自己的部署环境，拥有足够清楚的权限边界、可用的日志、相对可信的测试设施，以及能够快速撤回变化的机制。一次 CSS 调整和一次账户权限迁移，即使都可以由模型写出来，可能造成的损失也截然不同。

Ball 的示例让我们看到一种可能的新组织形态，同时也提醒我们：**速度不是免费获得的，它的一部分成本已经转移到验证基础设施与运行权限治理上。**

## 四、另一种回答：不是停止审查，而是重新定义审查的对象

九月二十八日，Addy Osmani 发表 [《The Code Nobody Reads》](https://addyo.substack.com/p/the-code-nobody-reads)，直接回应 Ball。他也不再坚持所有 AI 代码都必须经人逐行审阅，但认为每次变更仍需要审查，也需要一个对是否交付负责的人。

十月十四日，他进一步写了 [《Agentic Verification》](https://addyo.substack.com/p/agentic-verification)，把注意力放在 Agent 自己能够运行的检查循环上：端到端用户流程、基于性质的不变量检查、新旧版本的差异测试，以及足够快速、确定性的反馈。

这并不是与 Ball 简单唱反调。两人的方向有相当大的重合：人类需要从重复阅读代码中解放出来，让软件自己尽可能多地产生可以核验的证据。分歧主要在于语言、风险偏好和强调的部分。Ball 喜欢宣布旧形式的死亡，Osmani 则更关心：替代它的新机制有没有真的建立起来。

以账户权限为例，一个模型生成的新页面可能通过了构建、截图对比和常规操作测试，但真正决定它能否上线的，往往是另一些问题：用户能否访问不属于自己的数据？退出登录后，已有连接是否立即失效？失败重试会不会意外重复执行操作？旧客户端还能不能正常工作？

这些问题不一定要求人类读完所有实现行数，却要求有人定义边界、设计反例、检查真实运行链路。尤其不能把“Agent 说自己测过”当作与实际环境独立的证据。

一个危险的场景是：同一个 Agent 误解需求，又根据相同的误解编写测试，最后用自己通过的测试证明自己正确。自动验证减少了人工工作量，却不会凭空产生正确的验收标准。这就是为什么验证结果的来源、独立性和覆盖边界值得比以前更认真地记录。

## 五、终端、开源、好代码：哪些消失的是形式，哪些不是？

Ball 的剩余判断也可以沿着这条线重新理解。

他说终端将死。也许将来人不必记住一堆命令参数，直接用自然语言请求系统完成操作；但这不表示 Shell、CLI 与机器可调用接口毫无价值。恰恰相反，Agent 要稳定操作一个系统，往往需要比人更明确的工具合同、退出码、结构化输出和可复现环境。**终端作为人的主要界面可能退场，命令式能力作为机器接口却可能留下来。**

他说传统意义上的好代码不一定还重要。代码缩进、行宽、命名偏好里，确实有大量面向人类阅读的约定可以重新评估。但模块边界、数据一致性、权限隔离、故障可观测性、性能上限并不只是为了让开发者看得舒服。它们决定系统会不会失控，以及一项修改能否在可接受的范围内被验证、定位和撤回。

他说现有开源模式不再合理，因为人工代码审查可以被机器审查取代。这指出了开源协作的一部分成本可能降低，却没有解决另一部分：谁决定项目方向，谁维护兼容性，谁解释许可证与供应链风险，谁在维护者离开后承担持续责任。能生成代码与愿意维护公共基础设施，不是同一种经济行为。

他甚至把 Token 称为新的计算范式，并预测拥有足够 Token 的人将获得新的生产优势。这个判断抓住了一个现实的资源问题：模型能力、调用预算、推理延迟和反馈循环正在影响谁能以什么成本制造软件。但把 Token 当作计算的唯一中心也可能忽略另一半世界：存储、网络、能源、确定性执行与长期运行中的基础设施并不会因为入口变得自然语言化就消失。

这些预测中有些会应验，有些可能只应验一半。与其争论词语的生死，不如追踪那些旧机制究竟承担了什么职责，以及新机制是否真的接过了它们。

## 六、真正稀缺的东西，开始从代码移向可信的交付

我们已经能看见一些变化：程序的初始实现更快了，一次性的自动化脚本更容易了，工程师也能同时推动从前必须串行完成的多个任务。可另一个现象也同样明显：需求理解、环境准备、权限批准、测试可靠性、部署稳定性和事后排障，并没有按照代码生成速度同步消失。

这会改变工程团队的价值分配。过去，一个困难功能可能首先卡在“有没有人能写”；未来，同一个功能更可能卡在“有没有人能准确描述要做成什么、证明它做成了，并对失败的后果负责”。这不是把工程师降格成向 Agent 派发工单的传声筒。恰恰相反，单纯传话、转发测试结果的人价值会下降，而能够识别错误目标、约束系统风险、组织真实验证的人价值会上升。

但这里也应保留一个重要限定：不是所有行业、所有规模、所有软件都处于同样的转型阶段。一个可随时回滚的内部工具、一个处理付款的系统、一段控制真实设备的程序，能够接受的失败方式完全不同。用一家 AI 工具创业公司的极端工作流，直接裁判其他所有工程场景，容易把技术可能性误写成普遍义务。

Ball 的十六条预测，最值得保存的不是任何一句“已死”，而是他逼迫人们重新回答的问题：当写代码不再足够稀缺，我们曾经用代码能力代表的那些更大的能力，要如何单独被辨认和衡量？

**代码仍然会被执行。它是否由人类逐行读过，也许不再是最重要的问题。重要的是，当它真正接触用户、数据、金钱和现实世界时，有没有人知道它应该做什么，有没有办法看见它实际上做了什么，以及出了问题以后，谁能让事情停下来。**

这也是软件工程的新难题。它比宣布某个工具死亡慢一些，也困难得多。
