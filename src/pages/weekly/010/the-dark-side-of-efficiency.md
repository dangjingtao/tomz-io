# 效率的暗面

前几天，Reddit 的 Claude Code 社区出现了一篇帖子。作者说，他所在的公司一年前宣布，今后所有编程工作原则上都要交给 AI Agent 完成，程序员如果想亲自写代码，反而需要说明理由。

刚开始的半年，效果很好。团队交付的功能比以往更多，开发速度也明显加快。

一年之后，情况有些不对劲。

按照发帖者的说法，公司代码库已经膨胀到原来的三倍。AI 经常重新编写已经存在的工具函数，同一个功能在系统里出现好几个版本。过去负责认真审查代码的两名程序员也离开了。

CodeRabbit 仍然会给每个 PR 提出审查意见，但团队里已经很少有人能够判断这些意见到底有没有价值。大家干脆把它们全部标记为已解决。

更讽刺的是，管理层最近又开始鼓励员工亲自写代码。发帖者发现，自己过去一个下午就能完成的任务，现在居然需要两天。

这篇帖子无法独立核实。我们不知道这家公司是谁，也不知道作者有没有夸大事实。

不过，评论区里有一个问题很有意思：如果软件已经不是程序员自己写的，我们应该怎样重新建立对它的理解？

## 代码改得比人看得快

11 月初，开发者 Ryan Prior 写了一篇文章，借用了信号处理中的奈奎斯特极限（Nyquist Limit），来解释 AI 编程可能遇到的问题。

奈奎斯特采样定理告诉我们：对于满足特定条件的连续信号，想要无失真地重建它，采样频率必须高于信号最高频率的两倍。

比如，一个正弦信号每秒振荡 5 次，采样频率需要高于每秒 10 次，才具备准确还原的条件。

Ryan 认为，软件开发也有类似的问题。

过去，程序员编写代码的速度有限。一段代码写出来以后，还要经过阅读、修改、测试和调试。程序员在这个过程中逐渐熟悉系统。

现在，AI 可以连续编写大量代码，甚至同时修改好几个模块。生成速度提高了，但人类阅读和理解代码的速度没有发生同等程度的变化。

于是，代码库可能每天都在增长，而开发团队对它的了解却越来越少。

Ryan 主张控制系统变更的节奏，让人有足够的时间观察、检查和更新对系统的认识。

![奈奎斯特极限类比：同一变化轨迹，稀疏观察与密集观察得到的认识不同](https://assets.tomz.io/jianpi/010/nyquist-analogy-v1.svg)

当然，奈奎斯特定理不能直接套用到软件工程。代码不是周期信号，读两次代码也不能保证理解得比读一次更好。

一天内修改十次、最后完整审查一次，可能比每次修改后匆忙看一眼更有效。

但是，这个比喻仍然提出了一个问题：当软件可以无限加快生产速度，谁来保证有人知道它是怎样工作的？

测试可以告诉我们某些功能是否正常，代码审查可以发现一些明显的缺陷，但这些手段不一定能回答另一个问题：为什么系统要这样设计？

## AI 干活，人为什么更累了

还有一个问题。既然代码由 AI 编写，程序员是不是应该越来越轻松？

德国技术博主 Constantin Gonzalez 今年 7 月写了一篇文章，描述了自己的经历。

有一天，他在慕尼黑的一处共享办公空间待了五个小时，同时推进三个项目：准备博客文章、贡献开源代码、修改网站的数据分析功能。

三个项目都有 AI Agent 负责执行。他只需要检查成果、作出决定、交代下一步任务，然后切换到另一个项目。

五个小时下来，事情推进得很顺利。

可是回家以后，他发现自己异常疲惫。那种感觉很像连续参加一整天的工作面试，虽然身体没有做什么重活，脑子却已经转不动了。

Constantin 借用餐厅厨房来解释这件事。

以前，程序员像厨师，需要亲自备菜、切菜、烹饪。现在，有了一群 AI 助手，厨师可以专心分配任务、检查菜品、决定下一道菜怎么做。

听起来很理想。问题是，餐厅里有专门的订单架，主厨不用把每一道菜的进度都记在脑子里。

而使用 AI Agent 时，很多人并没有这样的管理工具。

一个 Agent 正在修改代码，另一个在搜索资料，第三个刚刚交付结果、等着审查。虽然工作已经分派出去，程序员脑子里还是要记着这些事情。

更重要的是，AI 接走的往往是比较轻松的执行工作。剩下的事情却大多需要人作出判断。

审查一段代码是否可靠，决定下一步如何修改，判断两个 Agent 的结果为什么互相矛盾。这些任务通常比单纯执行更耗费注意力。

于是，过去写代码、等待编译、调试程序之间自然形成的间歇消失了。每当一个 Agent 开始工作，程序员就可以去处理另一个任务。

一天下来，事情可能做得更多，人也更累。

![三个 Agent 分别承担写作、编码和检索，最终仍需要人审查和决策](https://assets.tomz.io/jianpi/010/agent-attention-v1.svg)

Constantin 后来开始限制同时进行的任务数量，为每项委托写清楚要求，在交接工作以后安排休息，而不是随时盯着 Agent 的运行状态。

这些做法并不复杂，但提醒了我们一件容易忽略的事：机器能够持续工作，并不代表人能够持续决策。

## 多出来的效率去了哪里

团队失去维护能力、代码改得比人看得快、程序员不写代码却更累——这些情况未必同时出现，也不能全算作 AI 的问题。

重复实现、知识流失和低质量审查早就存在。AI 带来的新变化，是制造代码的成本大幅下降。

过去，一个团队可能因为人手不足，决定暂时不开发某项功能。现在，只要启动 Agent，就能很快得到一个看起来可以运行的版本。

但随之而来的测试、维护、文档更新、技术支持和故障排查，并不会因为代码生成得快就自动消失。

![从 AI 生成到人工审查、测试验证、发布上线和维护返工的五个环节](https://assets.tomz.io/jianpi/010/hidden-delivery-costs-v1.svg)

例如，一个 Agent 用十分钟写完新功能，另一个 Agent 又用十分钟补齐测试。这当然可能是一件好事。

但如果代码引入了新的依赖，修改了原有数据结构，或者悄悄复制了一套已经存在的业务逻辑，团队仍然需要花时间发现和处理这些问题。

有些问题当场就能发现，有些则可能在几个月以后才暴露出来。

因此，判断 AI 是否提高了软件开发效率，不能只看生成了多少代码，或者一天合并了多少 PR。

还要看这些代码后来是否容易维护，有多少功能真正被使用，发生故障时团队能否迅速找到原因。

这里也存在另一种可能：AI 本身可以帮助人理解软件。

它能够搜索整个代码库，解释陌生模块，列出调用关系，发现重复实现，甚至为一段多年无人维护的程序补齐测试。

我们没有理由认定，只有亲手编写代码才能理解代码。

问题在于，使用这些能力同样需要投入时间。一个团队如果只要求 Agent 不断交付功能，却不安排代码整理、系统学习和架构维护，AI 未必会主动替它完成这些工作。

## 需要重新计算的成本

软件行业一直在设法减少重复劳动。从高级编程语言、框架到云计算，许多麻烦逐渐交给了工具。AI 编程也是这一过程的延续，让更多人有机会开发软件，也让小团队能够承担过去做不到的项目。

但代码生成得快，有些成本反而更加显眼。

以前，一个程序员需要花一下午编写代码。现在，可能十分钟就能生成初稿，却需要另外半小时决定是否接受，再花时间确认它没有破坏其他功能。

认真完成这些检查，AI 带来的效率仍然可能非常可观。为了追求交付数量而省掉它们，节约下来的时间却可能在将来变成维护成本。

管理多个 AI Agent 也是如此。

一个人能够同时启动十个 Agent，不代表他能同时认真验收十份工作。增加 Agent 数量很容易，增加可靠的判断能力却困难得多。

也许，今后的软件团队需要学习的不只是如何写出更好的提示词，还包括如何控制工作数量、保存设计依据，以及决定什么时候应该停止继续生成代码。

这听起来似乎没有那么令人兴奋。

毕竟，展示一个 Agent 在几分钟内完成复杂任务，比展示一个团队花了两天时间审查和整理代码，更容易吸引注意力。

但软件最终还是要被人使用、维护和信任。

AI 可以让我们更快地把一件事情做出来。

至于它是不是真的做好了，仍然需要有人知道该怎样判断。
