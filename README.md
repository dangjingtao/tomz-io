# 见π Radar 素材库

这个分支只保存《见π》的编辑采集材料，不参与 Tomz.io 构建，也不允许合并到 `main`。

编辑定位、读者对象、写作原则与正式成刊规则见 [`EDITORIAL_PRD.md`](./EDITORIAL_PRD.md)。本文件只负责定义素材库与采集协议。

## 固定位置

- Repository: `dangjingtao/tomz-io`
- Branch: `editorial/jianpi-radar`

## 目录约定

```text
YYYY/
└── Wxx/
    ├── YYYY-MM-DD.yml
    ├── discussion.yml
    └── shortlist.yml
```

- `YYYY-MM-DD.yml`：每日 Radar 采集结果，以及当日进入候选池的现场材料。
- `discussion.yml`：Tomz 与 Mira 在聊天中讨论出的、值得进入候选池的材料。
- `shortlist.yml`：仅在 Tomz 明确启动编辑选题阶段时使用；**日常 Radar 不得自动创建或改写**。

## 素材来源

《见π》允许同时从外部世界和真实现场收集材料：

1. **公开 Radar**：技术、产品、开源、研究、科学、硬件、设计、Web、开发工具、中国开发者现场，以及“鬼集”等异常但值得多看一眼的东西。不要让 AI / Agent 自动占满视野。
2. **Mira Agent Radar**：适合从专业 Agent 工程语境继续翻译给更广泛技术读者的信号与判断。
3. **Mira 稳定性周报**：Mira 自己真实发生的失败、回归、治理、测试、发布、跨端合同、Review、Control Room 等工程现场。
4. **Tomz 工作周报**：产品、协作、硬件、设计系统、测试、需求管理与 AI 落地等工作现场。默认视为私密材料，只允许脱敏后提炼普遍问题，不得把公司或人员可识别信息原样带入候选池。
5. **人物与传记雷达**：每周主动扫描与当周时事发生真实关联的著名人物——逝世、纪念日、奖项、作品重映、新档案公开、重大争议、技术突破或公共事件，都可以成为重新阅读一个人的入口。目标不是做百科式人物小传，而是回答“为什么是这周，又为什么是这个人”。
6. **Tomz × Mira 讨论**：双方在日常讨论里形成的新判断、关联、反例、怪东西与尚未成熟但值得保留的想法。

### 开源项目发现入口

- [HelloGitHub](https://hellogithub.com/)（[月刊](https://hellogithub.com/periodical) · [开源仓库](https://github.com/521xueweihan/HelloGitHub)）：作为长期公开 Radar 候选来源，优先浏览新一期与项目详情。它是**发现入口**，不是《见π》可直接转载的正文；选题入池须回到项目上游仓库核实作者、实际能力、版本、许可证及是否已被《见π》收录。同一项目在 HelloGitHub 已出现过，不代表它是当周新发布或新开源。

## 采集优先级：以科技圈为主场（2026-11 修订）

**主场是科技行业；核心问题是技术、产品和生意正在发生什么变化。** 观察优先级不等于每期配额，某一方向没有高信号就不凑数。

1. **AI 业界（第一优先）**：模型与研究突破、AI 产品、开源模型与工具链、平台和公司竞争、行业落地、开发者的真实使用反馈及失败案例。Agent 是其中一部分，不能只追 Agent 工程。
2. **全球创新产品及中国落地机会（第一优先）**：追踪海外新产品、独立开发者、小团队、垂直 SaaS、真实需求、商业模式、定价、获客、经营数据与失败复盘；同时独立观察中国市场、中文用户、微信等本地生态、支付/分发/监管和小团队可行性。不把海外产品简单翻译成中国创业机会，也不强制所有产品都找到中国对应市场。
3. **科技新闻（高优先）**：重大科技产品与公司动态、开发工具、开源、Web/互联网、软硬件、科研产业化、平台规则及真正影响创业与普通技术使用者的政策。
4. **能力拐点（主动寻找）**：新模型、新 API、新开源协议、算力/推理成本下降、终端本地能力、硬件门槛下降等，让过去昂贵、封闭或不可能的事情开始可做。追问「原来做不到什么、现在谁能做到、成本如何改变、证据在哪」，但**技术可行不等于市场需求已获验证**。
5. **历史、制度与人物（纵深）**：重要史料、科技/创业史，也保留独立有价值的历史与制度问题；可参照 `dangjingtao/qishu` 当前研究材料，但不得借用未核实结论。每周人物与传记扫描仍为必做，不为写人物稿而写人物稿。
6. **开放发现（有惊喜才收）**：科学、设计文化、城市与人的现场、纯粹有趣的个人作品及「鬼集」，不需要强行附会商业价值。

**发现入口不是证据**：关注一手厂商/开发者博客、产品原站、论文与 release notes、GitHub、Hacker News、Product Hunt、Show HN、HelloGitHub、创业社区及中文开发者现场。独立博客和个人 RSS 是额外的长期内容信源：重点读真实实践、经营复盘、反例与个人观点，明确作者归属；这期不强制引入专门的「博客漫游」选材流程，社群参与/留言/申请加入另行讨论，Radar 不自动代用户发言。

### 创业与能力线索如何判断

- **已发生的事实**：产品确实上线了什么、谁在使用、原作者展示了什么结果；优先原始链接与可核对数据。
- **发现的机会**：谁的哪项需求没有满足？为什么现在可能成立？对中国市场的小团队意味着什么？有哪些支付、获客、竞争、合规与平台约束？
- **明确的不确定性**：宣传稿、单个创业者自报收入、点赞量、等待名单不等于可重复的商业验证；无数据时写假设、反例或 `hold`，不打虚假的「创业潜力评分」。
- **反向信号同样重要**：倒闭、失败、分发瓶颈、用户不买单、单位经济性崩溃，均可成为比成功故事更好的素材。

## 候选字段

```yaml
- title:
  url:
  source:
  radar:
  topic:
  discoveredAt:
  origin: radar | discussion | field-note
  note:
  status: candidate | selected | hold | skip
  # 可选：kind: news | product | capability | opportunity | history | other
  # 可选：opportunityNote: ""  # 机会判断/中国市场假设，和 note 中的事实分开
  imageUrl: null
  imageSourceUrl: null
  imageSource: ""
  imageNote: ""
  imageStatus: none | verify-rights
```

上述九个基础字段不可缺失；图片相关五字段也应逐条记录，找不到可核权的图片时明确用 `imageUrl: null`、`imageStatus: none`，保留来源/版权说明。可选 `kind` 与 `opportunityNote` 不要求回填历史文件；对有创业价值的消息尤其要把原始事实与机会判断分离。不得下载图片或上传到 R2。

`origin` 语义：

- `radar`：公开 Web Radar 或其他 Radar 来源。
- `discussion`：Tomz × Mira 的讨论材料。
- `field-note`：Mira 稳定性周报、Tomz 工作周报及其他真实工程 / 工作现场。

对于没有公开 URL 的 `field-note`，`url` 可以为空，但 `source` 与 `note` 必须说明素材来自哪类现场以及公开使用时需要怎样脱敏。

## 编辑规则

1. Radar 可以搜索、去重、聚类、摘要和形成候选，但不能自动发布正式《见π》。
2. 每日采集优先保存高信号项目、产品、论文、讨论、现场经验与“鬼集”候选，不为数量凑数。
3. 主动扩大观察面。AI / Agent 是重要来源，但不是整本《见π》的唯一世界。
4. 周一额外回看最近 7 天进行去重、信号校验、续注与覆盖面审视，**不得自动生成或更新 `shortlist.yml`**，除非 Tomz 在独立的编辑阶段明确要求；任何自动采集都不得擅自确定最终选题。
5. **每周必须主动扫描至少一轮“人物传记候选”**。候选人物必须与当周发生的真实事件存在编辑关系；可以不入选，但不能因为本周科技新闻很多就跳过人物扫描。若人物近期已被《见π》充分写过，应优先做“回看/续注”或直接跳过，避免重复传记。
6. Tomz 与 Mira 在日常聊天中讨论出值得保留的新判断、项目或怪东西时，允许直接回传当前周的 `discussion.yml`。
7. `field-note` 不是内部周报转载。只有能够抽象成普遍问题、经验或反例的内容才进入候选池；工作材料必须先脱敏。
8. Radar 可以发现关联，但不能替 Tomz 与 Mira 完成最终编辑判断。候选之间是否构成一期主题、哪条值得展开成主文，由正式编辑阶段决定；即使候选与正在编辑的专题有关，也不得擅自改动那一期的稿件、目录或选材。
9. 正式《见π》内容必须经过 Tomz 编辑判断后，另行进入网站正式内容流程。
10. 此分支永远不作为生产代码来源，不反向覆盖 `main`。

## 每日运行与失败兜底

1. 每次先读取本分支最新 `README.md` 与相关编辑规定；读取当前周最近候选，按 URL、同一事件与话题去重。同一事件的新进展优先更新原日期记录，保留初始发现时间和可追溯来源。
2. 仅在 `editorial/jianpi-radar` 分支新增或更新每日 `YYYY/Wxx/YYYY-MM-DD.yml`、必要时补充 `discussion.yml`；不修改 `main`、`preview/*`、`content/*` 或其他生产/发布分支。保存前核对必填字段、图片版权状态，写后重新读取核验。
3. 若 GitHub 写入失败，制作当天**完整 YAML 待入库稿**，上传到已连接 Google Drive 的「《见π》Radar 待同步」目录；下次运行优先检查积压稿，按既有 URL/主题去重后同步。若 Drive 也不可写，保留可下载待入库稿并简短报告阻塞；不可因此停用定时任务。
4. 仅在特别强的新信号或需要用户介入的持续故障时主动提醒；普通采集成功不打扰。**任何自动运行都不生成 shortlist、不替编辑确认选题、不发布周刊。**
