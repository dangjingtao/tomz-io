# Tomz.io 内容架构原则

> 本文是 tomz.io 关于博客、系列、书架、内容归档、公开 URL 与 SEO 的正式设计原则。
>
> 对博客系列化、书架收录、内容迁移、URL、canonical、sitemap 或相关导航做任何新增、调整前，必须先阅读本文。

## 1. 设计目标

Tomz.io 同时承载即时写作与长期整理，两者不能混成一套层级。

- **博客**负责记录事情发生时的文章，保持轻量、时间流和少量稳定栏目。
- **系列**负责表达多篇文章之间的连续关系，不承担新的正文归属。
- **书架**负责后期编排与长期阅读，把已经成熟的文章重新组织成更完整的阅读结构。

核心原则：

> **文章是什么，和文章后来被放进什么阅读结构，是两回事。**

## 2. 三层内容模型

### 2.1 栏目 Group

栏目回答：**这篇文章本身属于什么性质的内容？**

例如：

- 共同思考；
- 开发者生活；
- Mira 来信。

栏目是文章的一级公开归属，可以影响博客导航、页面语义与当前公开路径。

栏目数量应保持克制。不得因为出现一个新系列就新增一个一级栏目。

### 2.2 系列 Series

系列回答：**这篇文章与哪些文章属于同一条连续探索？**

例如：

- OPC 探索；
- 重新工作后的周记；
- 某个持续的产品或技术实验。

系列是逻辑关系，不是新的物理目录，不要求产生第二份正文，也不应默认改变文章 URL。

推荐的数据表达方向：

```yaml
series:
  id: opc-exploration
  title: OPC 探索
  order: 1
```

具体字段实现可以以后调整，但语义必须保持独立于 `group`、`title` 与公开 URL。

### 2.3 书籍 Book

书籍回答：**哪些已经形成积累的内容，值得被重新编排成一份连续阅读作品？**

书架是后期组织视图。一本书可以引用既有博客文章作为章节来源，也可以包含原生书籍章节。

除非明确做内容迁移，书架收录本身不改变文章原始归属。

## 3. 默认采用逻辑归档

博客系列成熟后进入书架，默认采用：

> **逻辑归档，而不是物理迁移。**

也就是说：

- 原 Markdown 正文仍保持唯一事实源；
- 已发布博客 URL 默认保持不变；
- 原页面 canonical 保持不变；
- 原文章仍可出现在博客时间流中；
- 书架只增加“这篇文章属于哪本书、排在第几章”的组织关系；
- 不为了“归档”复制一份正文到 `/books/...`；
- 不为了“归档”删除原博客文章或制造第二套可索引正文 URL。

因此：

```text
博客 = 发生现场
系列 = 逻辑关系
书架 = 后期编排视图
```

三者可以同时指向同一篇内容，但正文实体只有一个。

## 4. URL 与 SEO 稳定原则

已经公开并被索引的文章 URL，应视为长期资产。

普通的系列化或书架归档不得仅为了目录整齐而更换 URL。

默认要求：

1. **一个正文实体只有一个 canonical URL。**
2. 书架索引页可以拥有自己的 URL 和 canonical，但不得生成同一正文的第二份可索引全文页面。
3. 书架章节若只是引用博客文章，应链接回原文章 canonical。
4. sitemap 不应因为逻辑归档而重复收录同一正文的多个 URL。
5. Open Graph、JSON-LD、Article 元数据应继续对应原正文实体。
6. 外部链接、历史分享链接和搜索引擎已建立的索引关系应尽量保持稳定。

如果未来确实需要把一篇已发布文章永久迁移成书籍原生章节，必须作为单独的迁移任务处理，并明确设计：

- 新旧 canonical；
- 301 / redirect 策略；
- sitemap 更新；
- 内部链接更新；
- 结构化数据；
- 搜索引擎重复内容风险。

不得把这种迁移作为“收入书架”的默认动作。

## 5. 标题与系列展示分离

文章 `title` 默认表达文章本身的标题。

系列名称、期数或章节序号应优先由独立 metadata 和页面展示层表达，例如：

```text
OPC 探索 · 01

一人公司，不是一个人做完一家公司
```

而不是长期依赖：

```text
OPC 探索（一）：一人公司，不是一个人做完一家公司
```

这样可以避免标题同时承担文章名、系列名、排序号和归档状态，减少未来改编、成书或跨入口展示时的耦合。

现有已经写入标题的系列前缀可视为迁移期现状；在 series metadata 与展示能力正式落地前，不要求为了形式统一立即重写所有历史标题。

## 6. 逻辑归档与历史归属纠正不是一回事

必须区分两类操作：

### 普通归档

文章原本就是合法的博客内容，只是后来形成系列或被收入书架。

此时：

- 默认不移动物理文件；
- 默认不改变 URL；
- 默认不改变 canonical；
- 只增加系列 / 书籍的逻辑关系。

### 历史归属纠正

文章过去放错了内容体系，原目录、URL、作者语义或栏目本身就是错误的。

例如 `docs/AUTHORSHIP.md` 中已经明确规定的《谎颜》历史归属调整。

此时可以按专项规则做物理迁移和 URL 调整。

**不得从《谎颜》这类历史纠正特例，类推出“博客收入书架就应该搬文件和换 URL”。**

## 7. 保持博客轻量

博客页不承担完整知识库导航职责。

默认不因为系列增多而在博客首页叠加大量一级入口、树状目录或复杂筛选器。

优先保持：

- 时间流；
- 少量稳定栏目；
- 轻量系列标记；
- 必要时提供进入系列或书架的入口。

更重的目录、章节顺序、连续阅读和长期整理交给书架。

## 8. 单一事实源

同一篇文章不得因为同时属于博客、系列和书籍而维护多份正文。

理想结构是：

```text
Article
├── group
├── series relation
└── book relation
```

而不是：

```text
/blogs/.../article.md
/books/.../chapter.md   # 复制正文
/series/.../01.md       # 再复制一次
```

任何实现如果要求为了多个入口同步维护多份正文，应先视为架构风险。

## 9. 执行要求

涉及博客系列、书架收录、逻辑归档、内容迁移、URL 或 SEO 的任务：

1. 先读本文；
2. 同时读取 `docs/AUTHORSHIP.md`，确认作者与内容归属；
3. 先判断任务属于“普通逻辑归档”还是“历史归属纠正”；
4. 普通逻辑归档默认保持原正文、原 URL 与 canonical；
5. 不得通过复制正文实现系列或书架；
6. 如确需 URL 迁移，必须单独说明 SEO 与 redirect 方案后再执行；
7. 修改后检查博客、系列、书架、sitemap、canonical 与结构化数据是否仍然只表达一个正文事实源。

---

本文优先约束 tomz.io 的内容组织方式。`docs/AUTHORSHIP.md` 继续负责作者、署名与内容归属；两者同时适用时，应分别满足，不得用内容归档规则覆盖署名规则，也不得用署名历史迁移特例覆盖普通逻辑归档原则。
