# Tomz.io 内容架构原则

> 本文是 tomz.io 关于博客、栏目、标签、书架、内容归档、发布时间、修改时间、公开 URL 与 SEO 的正式设计原则。
>
> 对博客归类、Tag 管理、书架收录、内容迁移、内容时间、URL、canonical、sitemap 或相关导航做任何新增、调整前，必须先阅读本文。

## 1. 设计目标

Tomz.io 同时承载即时写作与长期整理，但不应为每一种关系增加新的内容层级。

- **博客**负责记录事情发生时的文章，保持轻量、时间流和少量稳定栏目。
- **Group**负责表达文章本身的一级内容性质。
- **Tag**负责表达文章在谈什么。
- **Book**负责把连续、相关或已经形成积累的文章组织成长期阅读结构。

核心原则：

> **文章是什么，和文章后来被怎样组织起来，是两回事。**

同时保持克制：

> **不设置独立的 Series 内容层。需要连续归类的文章，直接交给 Book。**

## 2. 三层内容模型

### 2.1 栏目 Group

Group 回答：**这篇文章本身属于什么性质的内容？**

例如：

- 共同思考；
- 开发者生活；
- Mira 来信。

Group 是文章的一级公开归属，可以影响博客导航、页面语义与当前公开路径。

栏目数量应保持克制。不得因为出现一组连续文章，就新增一个一级栏目。

### 2.2 标签 Tag

Tag 回答：**这篇文章主要在谈什么？**

例如：

- AI；
- Agent；
- 产品；
- 工作；
- 写作。

Tag 是**全站共享的主题词表**，不是博客、书架、项目、作品各自维护一套词表。一个词在任何内容区域出现，都应遵守同一套语义和 canonical 写法。

Tag 是主题关系，不负责表达栏目，也不负责表达连续文章的归档关系。

因此：

- 不应仅因为文章位于「Mira 来信」就再添加 `Mira 来信` Tag；
- 不应仅因为文章位于「开发者生活」就再添加 `开发者生活` Tag；
- Book 原生章节也不应仅因为属于《一起学智能体》《谎颜》《读诗篇》等 Book，就把 Book / Group 名再次当作结构性 Tag；
- 不应为了把几篇文章串成一组而临时造一个 Tag；
- 如果某个词本身确实是文章主题，即使它同时也是一本 Book 的名称，也可以保留为 Tag，但不能依赖 Tag 承担 Book 的归档职责。例如 `OPC` 可以同时作为跨博客、项目内容的真实主题词。

#### Tag 收敛规则

Tag 管理采取“**受控 canonical + 保留必要细粒度**”的方式，而不是建立一个不允许增长的硬白名单。

1. **优先复用已有词。** 新建 Tag 前先检查全站是否已经存在同义或近义表达。
2. **同义词只保留一个 canonical 写法。** 当前明确统一：
   - `智能体` → `Agent`
   - `多智能体` → `Multi-Agent`
3. **不重复 Group。** 如果一个 Tag 与当前页面 `group` 完全相同，站点内容读取层会将其视为结构重复并剔除。
4. **规范化后去重。** 别名统一后产生的重复 Tag 只保留一个。
5. **不为了降低数量强行合并不同概念。** `AI Coding`、`AI Code Review`、`Coding`，或 `Tool`、`Tool Calling` 等只要语义确实不同，就不为了让统计更漂亮而合并。
6. **一次性 Tag 不是原罪。** 某个具体概念只在一篇文章里出现，只要它确实是该文的重要主题，就可以保留；不要用“出现次数少”作为删除依据。
7. **Tag 数量保持克制。** 普通内容优先选择少量真正影响发现与关联阅读的主题词，不设机械配额，也不因为正文顺带提到某个产品、技术或人物就必然加 Tag。

站点对外使用的 Tag 以 canonical 结果为准。历史 frontmatter 中已经存在的结构重复或旧别名可以渐进清理，不为了 metadata 整齐一次性制造几十篇正文的无意义 diff；**新内容和后续正常编辑应直接写 canonical Tag，不继续新增旧写法。**

Tag 的收敛逻辑集中在内容边界维护，不应由每个页面组件各自写一套过滤规则。

### 2.3 书籍 Book

Book 回答：**哪些文章需要被作为一组连续内容长期组织和阅读？**

这里的 Book 不要求内容一开始就是传统意义上的“书”。它同时承担连续文章归类与后期编排职责。

例如：

- OPC 探索可以作为一个 Book；
- 重新工作后的周记如果需要长期归档，也可以作为一个 Book；
- 一个持续的产品或技术探索，在形成连续阅读价值后也可以进入 Book。

Book 可以引用既有博客文章作为章节来源，也可以包含原生书籍章节。

**不再额外建立 Series / 系列 metadata 层。**

具体 Book metadata 的字段结构在真正实现时再按现有书架能力设计，不提前增加一套与书架重复的协议。

## 3. 默认采用逻辑归档

博客文章被收入 Book，默认采用：

> **逻辑归档，而不是物理迁移。**

也就是说：

- 原 Markdown 正文仍保持唯一事实源；
- 已发布博客 URL 默认保持不变；
- 原页面 canonical 保持不变；
- 原文章仍可出现在博客时间流中；
- Book 只增加“这篇文章属于哪本 Book、排在什么位置”的组织关系；
- 不为了“归档”复制一份正文到 `/books/...`；
- 不为了“归档”删除原博客文章或制造第二套可索引正文 URL。

因此：

```text
Group = 文章是什么
Tag   = 文章在谈什么
Book  = 哪些文章被组织在一起
```

博客仍然是文章的发生现场，书架负责长期组织；正文实体只有一个。

## 4. URL 与 SEO 稳定原则

已经公开并被索引的文章 URL，应视为长期资产。

普通的 Book 归档不得仅为了目录整齐而更换 URL。

默认要求：

1. **一个正文实体只有一个 canonical URL。**
2. 书架索引页可以拥有自己的 URL 和 canonical，但不得生成同一正文的第二份可索引全文页面。
3. Book 章节若只是引用博客文章，应链接回原文章 canonical。
4. sitemap 不应因为逻辑归档而重复收录同一正文的多个 URL。
5. Open Graph、JSON-LD、Article 元数据应继续对应原正文实体。
6. 外部链接、历史分享链接和搜索引擎已建立的索引关系应尽量保持稳定。

如果未来确实需要把一篇已发布文章永久迁移成书籍原生章节，必须作为单独的迁移任务处理，并明确设计：

- 新旧 canonical；
- 301 / redirect 策略；
- sitemap 更新；
- 内部链接更新；
- 结构化数据；
- 搜索引擎重复内容风险。

不得把这种迁移作为“收入书架”的默认动作。

## 5. 内容时间模型

Tomz.io 的公开内容统一区分两个时间概念：

```text
publishedAt = 内容第一次公开发布的时间
modifiedAt  = 当前正文实体最后一次实际修改进入 Git 历史的时间
```

这套时间模型适用于博客、Book 原生章节、项目文章、作品说明等公开正文内容，不为不同内容区域各自维护一套时间语义。

核心原则：

> **Git 负责可以验证的修改事实，frontmatter 只补 Git 无法可靠知道的历史发布时间。**

### 5.1 发布时间 `publishedAt`

发布时间允许人工覆盖，但不要求为历史文章一次性补齐精确时间。

现有 frontmatter `date` 继续作为兼容字段和作者声明的发布日期，例如：

```yaml
date: 2026年8月27日
```

如果作者明确知道精确发布时间，可以新增覆盖字段：

```yaml
publishedAt: 2026-08-27T09:07:05+08:00
```

`publishedAt` 是发布时间的最高优先级人工事实。使用日期时间时必须带明确时区；如果只能确认日期，也允许使用 `YYYY-MM-DD`，不得为了字段完整伪造 `00:00:00`。

实际发布时间按以下优先级解析：

```text
1. frontmatter publishedAt
2. frontmatter date + Git 历史中的同日发布时间线索
3. frontmatter date（仅日期精度）
4. Git 中该内容源首次出现的提交时间
```

其中第 2 条的目标只是：**在人已经写明发布日期的前提下，用 Git 帮助恢复这一天内可验证的时分秒。** 如果该日期在 Git 历史中没有可靠匹配，就保持日期精度，不向后借用迁站、重构、镜像导入等提交时间。

因此，旧文章即使在当前仓库中首次出现得更晚，只要 frontmatter 已明确写有更早的 `date`，也不得把“进入当前仓库的时间”冒充原始发布时间。

需要在解析结果中保留时间精度概念，例如：

```text
publishedPrecision = datetime | date
```

它属于运行时 / 构建期派生信息，不要求作者手工维护。

### 5.2 修改时间 `modifiedAt`

`modifiedAt` **不设置人工 frontmatter 字段**，也不允许作者手工维护。

默认规则：

```text
modifiedAt = 当前正文源文件最近一次实际变更的 Git commit 时间
```

实现时应基于文件历史而不是文件系统 mtime，并在存在改名 / 移动历史时尽可能跟随文件历史（例如使用等价于 `git log --follow` 的策略）。

如果一个公开正文实体由多个源文件合成，则 `modifiedAt` 应取所有参与该正文实体的源文件最近一次有效修改时间中的最大值，而不是只看入口文件。

自动化提交只有在确实修改了该正文源时才会影响 `modifiedAt`；与正文无关的构建、部署或首页快照提交不应改变文章修改时间。

### 5.3 Git 历史不是旧站发布时间的替代品

Git 能证明的是**当前可见版本历史中的提交事实**，不是所有历史公开行为。

因此必须区分：

- 新文章：首次创建提交通常可以作为发布时间的重要证据；
- 老文章：可能经历旧站迁移、整站 mirror、目录重构或历史导入；
- 人工 `date` 早于当前仓库首次提交时，应优先尊重作者声明的日期；
- 无法确认时分秒时，只显示日期，不推测。

不得为了让所有文章都有“精确到分钟”的时间，而人为制造虚假精度。

### 5.4 构建期生成，而不是浏览器查询 GitHub

内容时间应在构建阶段统一计算，形成站点内容数据的一部分，例如：

```text
source path
→ first commit
→ latest commit
→ publishedAt
→ modifiedAt
→ publishedPrecision
```

页面运行时不应为每篇文章调用 GitHub API，也不应由 React 组件各自执行时间推算。

生产构建和负责验证时间元数据的 CI 必须拥有足够完整的 Git 历史；如果使用 GitHub Actions checkout，实现阶段应显式提供完整历史（例如 `fetch-depth: 0`），避免浅克隆导致本地与线上推算结果不同。

生成的时间映射属于构建派生数据，不应成为第二套需要人工维护的事实源。

本地环境如果确实不存在 `.git` 历史，可以降级使用 `publishedAt` / `date`，并缺省 `modifiedAt`；生产构建则不应静默用文件 mtime 冒充 Git 修改时间。

### 5.5 页面展示

所有公开正文页面都应能够展示发布时间和修改时间。

默认展示策略：

- 列表 / 时间流：优先只展示 `publishedAt`，保持信息密度克制；
- 正文详情：展示明确标签的“发布于”和“更新于”；
- 如果发布时间只有日期精度，就只显示日期；
- 如果发布时间与修改时间完全相同，可以避免重复展示两份相同时间；
- 时间显示统一按站点确定的显示时区格式化，不在各组件自行解释时区。

示例：

```text
发布于 2026年8月27日 09:07 · 更新于 2026年8月30日 18:41
```

### 5.6 SEO 与结构化数据

公开正文的结构化数据应使用同一套内容时间结果：

```text
datePublished = publishedAt
dateModified  = modifiedAt
```

如果 `publishedAt` 只有日期精度，结构化数据就使用日期，不补造时间。

后续 sitemap 如果输出 `lastmod`，应统一使用 `modifiedAt`；不得由页面、JSON-LD、sitemap 分别推算三套修改时间。

发布时间人工覆盖、Git 推算、可见页面、JSON-LD 与 sitemap 最终必须指向同一套归一化时间数据。

## 6. 标题与 Book 展示

文章 `title` 默认表达文章本身的标题。

如果某篇文章属于一个 Book，Book 名称和章节 / 顺序信息可以由书架关系或页面展示层表达，而不要求再增加 Series 字段。

例如页面可以展示：

```text
OPC 探索 · 01

一人公司，不是一个人做完一家公司
```

现有已经写入标题的 `OPC 探索（一）` 等前缀可以暂时保留，不为了形式统一立即重写历史标题。

以后是否把 Book 名称与文章 title 彻底分离，应在书架关系真正落地时统一处理，不提前为此新建一层协议。

## 7. 逻辑归档与历史归属纠正不是一回事

必须区分两类操作：

### 普通归档

文章原本就是合法的博客内容，只是后来被组织进一个 Book。

此时：

- 默认不移动物理文件；
- 默认不改变 URL；
- 默认不改变 canonical；
- 只增加 Book 的逻辑关系。

### 历史归属纠正

文章过去放错了内容体系，原目录、URL、作者语义或栏目本身就是错误的。

例如 `docs/AUTHORSHIP.md` 中已经明确规定的《谎颜》历史归属调整。

此时可以按专项规则做物理迁移和 URL 调整。

**不得从《谎颜》这类历史纠正特例，类推出“博客收入书架就应该搬文件和换 URL”。**

## 8. 保持博客轻量

博客页不承担完整知识库导航职责。

默认不因为 Book 增多而在博客首页叠加大量一级入口、树状目录或复杂筛选器。

优先保持：

- 时间流；
- 少量稳定栏目；
- 必要且克制的 Tag；
- 必要时提供进入 Book / 书架的入口。

更重的目录、章节顺序、连续阅读和长期整理交给书架。

## 9. 单一事实源

同一篇文章不得因为同时属于博客和 Book 而维护多份正文。

理想结构是：

```text
Article
├── group
├── tags
├── content time
└── book relation
```

其中 `content time` 的发布时间可以由 frontmatter 补充历史事实，修改时间由 Git 派生；它们都不应再产生第二套人工台账。

而不是：

```text
/blogs/.../article.md
/books/.../chapter.md   # 复制正文
```

任何实现如果要求为了多个入口同步维护多份正文，应先视为架构风险。

## 10. 执行要求

涉及 Tag 管理、书架收录、逻辑归档、内容时间、内容迁移、URL 或 SEO 的任务：

1. 先读本文；
2. 同时读取 `docs/AUTHORSHIP.md`，确认作者与内容归属；
3. 先判断任务属于“普通逻辑归档”还是“历史归属纠正”；
4. 普通逻辑归档默认保持原正文、原 URL 与 canonical；
5. 不得通过复制正文实现 Book；
6. 不新增独立 Series 内容层，连续文章的归类直接使用 Book；
7. Tag 只表达主题，不用来替代 Group 或 Book；Tag 是全站共享词表，新内容必须优先使用 canonical 写法；
8. 不因一次 Tag 治理任务机械删除有意义的细粒度主题，也不因历史 frontmatter 存在旧写法就继续复制旧写法；
9. 发布时间按 `publishedAt > date + Git 同日证据 > date > Git 首次提交` 解析；无法证明时不得伪造精确时间；
10. `modifiedAt` 只从 Git 内容历史派生，不人工维护，不使用文件 mtime 冒充；
11. 如确需 URL 迁移，必须单独说明 SEO 与 redirect 方案后再执行；
12. 修改后检查博客、书架、sitemap、canonical、结构化数据和内容时间是否仍然只表达一个正文事实源。

---

本文优先约束 tomz.io 的内容组织方式。`docs/AUTHORSHIP.md` 继续负责作者、署名与内容归属；两者同时适用时，应分别满足，不得用内容归档规则覆盖署名规则，也不得用署名历史迁移特例覆盖普通逻辑归档原则。
