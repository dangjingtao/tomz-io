# 见π PRD v0.3

> 状态：Draft / 可施工约束稿  
> 产品名：见π（暂定；后续改名不影响内容模型）  
> 所属：Tomz.io 一级内容产品  
> 当前实现分支：`preview/weekly-v0-1`  
> 编辑素材分支：`editorial/jianpi-radar`  
> 生产分支：`main`  
> UI：信息架构已确定，具体视觉仍待定

## 1. 为什么做见π

Tomz.io 目前以博客、书架、作品、项目等长期内容为主，整体气质克制、稳定，适合沉淀完整文章与长期判断。

但很多值得注意的东西并不适合立刻写成长文：

- 新出现的 Agent / AI 工程实践；
- 开源项目的异常增长或新架构；
- 有意思的产品与工具；
- 中国开发者现场；
- 商业与分发变化；
- 研究、论文与值得读的材料；
- 历史、制度与旧材料中重新显出意义的东西；
- 很怪但值得看一眼的项目、论文、产品与用法；
- Tomz 与 Mira 在日常讨论中形成、尚不足以单独成文的判断；
- Tomz 主动提交、希望进入编辑判断的人工素材；
- 来自真实工程与工作过程、经过脱敏后仍有公共价值的现场材料；
- 本周已经在 Mira 官网、Tomz.io 等正式站点发布、值得在本期重新指向的周报、周记与文章。

见π用于承接这一类内容。

它不是“新闻周刊”，也不是“链接合集”，而是 Tomz × Mira 对外部世界进行持续观察、筛选、聚类与判断后形成的一期一期内容产品。

核心原则：

> **不是把这一周发生的东西都搬进来，而是留下这一周值得继续看的东西。**

## 2. 产品定位

### 2.1 一级内容产品

见π是 Tomz.io 的一级内容产品，与博客、书架、作品、项目等并列。

“周刊”仅描述当前发布节奏，不作为产品名或内容层级。

当前预期：

```text
Tomz.io
├── 博客
├── 见π
├── 投稿
├── 作品
├── 项目
├── 书架
└── 关于
```

### 2.2 不是 OPC 周报

OPC / Company OS / AI Employee / Agent Workforce / Harness / Control Plane / OpenClaw 等仍是重要观察主题，但只是见π Radar 的一部分。

见π的观察范围至少包括：

1. Agent / AI；
2. 开源项目；
3. 产品与工具；
4. 中国开发者现场；
5. 商业与分发；
6. 研究与值得读；
7. 历史 / 制度 / 旧材料；
8. 异常信号；
9. 鬼集。

### 2.3 Tomz 是主编

自动化可以：

- 搜索；
- 去重；
- 聚类；
- 摘要；
- 形成候选；
- 提出趋势判断；
- 生成编辑 shortlist；
- 形成草稿建议。

自动化不能：

- 代表 Tomz 做最终入选判断；
- 自动发布正式见π；
- 自动把候选写成 Tomz 的观点；
- 未经人工确认写入生产内容；
- 将素材分支反向合并进 `main`。

## 3. 内容模型

### 3.1 一期不是一篇文章，而是一次编辑

v0.3 正式废止 v0.2 的“一期一篇 Markdown”假设。

一期见π的正式单位是一个**期目录**。期目录至少包含一个 `index.md`，并可以按需包含若干独立详情文章。

建议结构：

```text
src/pages/weekly/
├── 001/
│   ├── index.md
│   ├── painful-and-full.md
│   ├── wiles-and-claude.md
│   └── norway-1905.md
├── 002/
│   └── index.md
└── ...
```

其中：

- `index.md` 是该期唯一的**编辑编排事实源**；
- 独立详情 Markdown 只为真正值得展开的内容存在；
- 一条素材入选见π，不等于必须生成一篇详情文章；
- 已经在其他正式站点发布的内容，可以只在 `index.md` 中以“标题 + 编辑简介 + 原文链接”引用，不复制正文；
- Radar / shortlist 不直接驱动生产 UI，也不是公开内容事实源。

当前 `preview/weekly-v0-1` 中的 `src/pages/weekly/001-painful-and-full.md` 仍属于旧模型预览实现。正式施工时应把它视为创刊号封面文章候选，而不是把旧文件形态继续固化为内容模型。

产品最终 URL 是否使用 `/weekly`、`/jianpi`、`/pi` 或其他路径，仍列为 TBD。URL 决策必须单独考虑已有预览实现、SEO、canonical 与未来稳定性，不因产品改名立即迁移。

### 3.2 单期索引是编排事实源

一期的顺序、权重、简介与“是否有详情页”由该期 `index.md` 表达。

例如：

```md
## 封面文章

### [痛苦而充实的三个月](./painful-and-full)

创刊号从一场深夜里的互相采访开始……

## 值得读

### [从 Wiles 七年到 Claude 十一天](./wiles-and-claude)

被机器压缩的不是天才，而是形式化验证的成本……

## 本周已发布

### Mira 工程周报

这一周 Mira 在组织治理、稳定性和工程基础设施上发生了什么。

[去 Mira 官网阅读原文](https://mira.tomz.io/)

### 工作与生活周记

已经在 Tomz.io 发布的本周记录，在这里仅作为本期现场入口。

[阅读原文](https://tomz.io/)

## 鬼集

### OOMWOO：一台拒绝把家交给云的扫地机器人

短评……

[原始项目](https://example.com)
```

这里不要求所有条目都有详情页，也不要求已经上线的站内 / 跨站内容为了进入见π而再生成一份正文副本。

> **单期索引负责编辑；详情页负责展开；已发布内容保留原来的正文归属。**

### 3.3 四种内容重量

见π正式内容允许四种重量同时存在：

#### A. 封面文章

- 通常一篇；
- 代表本期最重要、最有情绪或最有编辑价值的内容；
- 可以是访谈、长文、现场文章或专题；
- 在单期索引页拥有最高视觉与内容权重。

#### B. 编辑文章

- 只有当 Tomz × Mira 真正形成了值得展开的判断时才独立成页；
- 可以从 Radar、人工投稿、讨论、field-note 等来源发展而来；
- 不要求长度一致，也不要求机械凑数量。

#### C. 短讯 / 鬼集 / 继续看

- 直接存在于单期索引页；
- 可以只有一段编辑短评和原始来源；
- 不为了“页面完整”强制生成低价值详情页。

#### D. 已发布内容 / 延伸阅读

- 用于 Mira 周报、Tomz 工作与生活周记、博客文章、工程现场文章等已经正式上线的内容；
- 在见π中只保留标题、1–3 句编辑简介和原文链接；
- 默认不复制正文，不生成第二个详情页，不改变原内容 canonical；
- 可以链接 Tomz.io，也可以链接 Mira 官网或其他由 Tomz / Mira 正式维护的站点；
- 只有当见π产生了新的、独立的编辑判断时，才另写见π详情文章，而不是把原文重新包装一次。

因此：

> **8–15 条入选项不等于 8–15 篇文章。已经上线的文章也不等于要在见π里再发一次。**

### 3.4 Frontmatter 只保存稳定元数据

单期 `index.md` 示例：

```yaml
---
title: "见π 001：痛苦而充实的三个月"
group: 见π
issue: 1
date: 2026年9月12日
lead: 创刊号从一场深夜里的互相采访开始……
tags:
  - AI
  - 写作
  - 产品
author:
  - mira
  - tomz
writingMode: co-authored
---
```

核心字段：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `title` | 是 | 本期标题 |
| `group` | 是 | 一级内容性质，目标为“见π” |
| `issue` | 是 | 永久期号，整数，不复用 |
| `date` | 是 | 作者声明的发布日期 |
| `lead` | 建议 | 本期导语 / 核心判断摘要 |
| `tags` | 建议 | 本期真正涉及的主题 |
| `author` | 是 | 按 Tomz.io 署名协议 |
| `writingMode` | 按需 | 共著等写作关系 |

详情页按实际内容使用现有 Tomz.io 文章元数据，并增加与所属期号的稳定关联；具体字段名称在正式实现前与现有 content parser 对齐，不在本 PRD 中提前发明第二套 schema。

注意：

- `issue` 是一期的永久身份；
- 单期目录负责一期 URL；
- 详情文章 slug 负责其自身 URL；
- Tag 只表达主题；
- 不用 Tag 表达“见π”结构；
- 不把栏目模块写成 `sections:` 之类结构化 frontmatter；
- 不在 frontmatter 重复维护单期正文的编辑顺序；
- 已发布内容的 canonical 永远属于原文，不因为被见π引用而改变。

正式落生产前，必须与 `docs/AUTHORSHIP.md` 的实际 author schema 对齐；当前预览样例不作为最终 schema 的唯一依据。

### 3.5 栏目是编辑语言，不是数据表

一期可以出现：

- 封面文章；
- 本期判断；
- 值得读；
- 产品与工具；
- 历史一页；
- 科学；
- 中国开发者现场；
- 本周已发布 / 延伸阅读；
- 鬼集；
- 继续看；
- 其他只属于当期的临时模块。

但不引入：

```yaml
sections:
  - type: agent-radar
  - type: product
```

原因：

> **常驻模块是编辑承诺，动态模块是这一期自己的性格。**

栏目不应该为了机器解析而变成填表系统。

## 4. 编辑素材库

### 4.1 固定仓库与分支

素材库固定为：

```text
Repository: dangjingtao/tomz-io
Branch: editorial/jianpi-radar
```

该分支只存编辑素材，不参与 Tomz.io 构建。

硬规则：

> **`editorial/jianpi-radar` 永远不允许合并到 `main`。**

正式内容只能经过人工编辑后，由正常内容分支进入生产。

### 4.2 目录

基础目录：

```text
YYYY/
└── Wxx/
    ├── YYYY-MM-DD.yml
    ├── discussion.yml
    ├── manual.yml          # 可选
    ├── field-notes.yml     # 可选
    └── shortlist.yml
```

含义：

- `YYYY-MM-DD.yml`：每日 Radar 保留下来的候选；
- `discussion.yml`：Tomz 与 Mira 日常讨论中值得回传的材料；
- `manual.yml`：Tomz 或编辑过程主动提交的人工素材；
- `field-notes.yml`：真实工程 / 工作现场中经过脱敏后值得保留的观察；
- `shortlist.yml`：周编辑汇总。

`manual.yml` 与 `field-notes.yml` 无内容时不要求机械创建空文件。

### 4.3 候选结构

基础结构：

```yaml
- title:
  url:
  source:
  radar:
  topic:
  discoveredAt:
  origin: radar
  note:
  status: candidate
```

`origin`：

```text
radar
discussion
manual
field-note
```

其中：

- `radar`：自动化或编辑 Radar 主动发现；
- `discussion`：Tomz × Mira 对话中形成的有效线索；
- `manual`：Tomz 主动提供的链接、截图、项目、论文或其他人工供稿；
- `field-note`：来自真实工程 / 工作现场，经过必要脱敏后保留的材料。

已经正式上线的 Mira 周报、Tomz 周记等内容不要求先复制进候选素材库才能被本期引用；编辑可以在确定本期结构时直接把它们作为“已发布内容 / 延伸阅读”编入 `index.md`。如需进入 Radar 的周编辑判断，也可以仅保留 URL 与简短说明，不复制正文。

`status`：

```text
candidate
selected
hold
skip
```

候选池是编辑工作台，不是网站内容，不进入 sitemap、搜索索引或正式站点构建。

## 5. Radar 工作流

### 5.1 日常采集

当前自动化任务名称：

```text
见π Radar
```

每天运行。

固定数据目标：

```text
dangjingtao/tomz-io
└── editorial/jianpi-radar
```

日常执行：

```text
公开 Web / GitHub / 一手来源
        ↓
多路 Radar
        ↓
真实性与新鲜度检查
        ↓
去重 / 降噪
        ↓
少量高信号候选
        ↓
YYYY/Wxx/YYYY-MM-DD.yml
```

目标不是完成机械配额。

参考容量：

- 一周浏览约 70–120 条原始信号；
- 留下约 25–40 条有效候选；
- 正式编辑建议约 8–15 条。

以上是工作容量目标，不是 KPI。质量不足时宁缺毋滥。

### 5.2 Radar 分类

基础 Radar：

- `agent-ai`
- `open-source`
- `product`
- `china-dev`
- `business-distribution`
- `research-reading`
- `history-politics`
- `anomaly`
- `ghost`

其中“鬼集”专门捕捉：

- 怪项目；
- 怪产品；
- 怪论文；
- 旧技术突然复活；
- 正常技术的非常规用法；
- 极小团队 / 单人做出异常体量的东西；
- 不一定重要，但看完会产生新问题的东西。

“鬼集”不以猎奇为目标，至少应满足“真实、有意思、有启发、值得立即理解”中的多项。

### 5.3 周一编辑

周一同一任务额外执行周编辑，不新增第二个定时任务。

```text
最近 7 天候选
    ↓
去重
    ↓
主题聚类
    ↓
趋势判断
    ↓
15–25 个编辑候选
    ↓
8–15 个建议入选项
    ↓
shortlist.yml
```

OPC 相关内容继续参与，但不拥有特殊结构地位。

周编辑产出的 8–15 个建议入选项只是**编辑候选集合**，不预先决定哪些必须成为详情文章。

## 6. 人工输入与对话回传

### 6.1 对话回传

Tomz 与 Mira 的日常聊天属于见π输入源之一，但不能机械归档聊天。

当讨论出现以下类型结果时，可以回传：

- 一个真正值得持续观察的新项目；
- 一个有证据支撑的新趋势判断；
- 一个适合“鬼集”的东西；
- 一个尚不足以成文但值得一周后再看的问题；
- 一条可能成为见π素材的产品 / 商业 / 开源 / 历史线索。

写入：

```text
YYYY/Wxx/discussion.yml
```

并使用：

```yaml
origin: discussion
```

普通聊天、情绪交流、未形成有效线索的随口想法不进入素材库。

### 6.2 人工供稿

Tomz 可以直接提交：

- URL；
- 截图；
- 项目名；
- 论文；
- 历史材料；
- 一句话线索；
- “现在还说不清为什么，但值得留”的东西。

人工供稿不需要先满足 YAML 格式，也不自动获得 `selected` 身份。

整理后使用：

```yaml
origin: manual
status: candidate
```

人工供稿与 Radar 候选在最终编辑会上接受同样的取舍。

### 6.3 Field Note

真实工程、产品与工作现场可以成为见π输入，但必须满足：

- 对公共读者有可理解的价值；
- 不泄露账号、密钥、客户数据、未公开商业信息或其他不应公开内容；
- 必要时先脱敏再进入素材池；
- 不把个人抱怨机械包装成“行业观察”。

使用：

```yaml
origin: field-note
```

### 6.4 已发布内容回链

Mira 工程周报、Tomz 工作与生活周记，以及其他已经上线的相关文章，可以直接进入本期编辑索引，但遵循“引用而不复制”：

- 见π负责说明“为什么这一期值得点开它”；
- 原站负责完整正文；
- 见π不为它复制第二份正文；
- 原文 URL / canonical / 作者关系保持不变；
- 如果原文以后更新，见π仍指向原文，而不是维护平行副本。

这类内容是本期编辑的一部分，但不是 Radar 必须重新抓取和改写的对象。

## 7. 编辑与发布流程

完整链路：

```text
Radar Sources ───────────────┐
discussion ──────────────────┤
manual submission ───────────┤
field-note ──────────────────┤
already-published links ─────┘
            ↓
        候选 / 可引用内容
            ↓
        周一 shortlist
            ↓
Tomz 删除 / 保留 / 调整 / 补充
            ↓
决定当期内容重量
  ├── 封面文章
  ├── 编辑文章
  ├── 短讯 / 鬼集 / 继续看
  └── 已发布内容 / 延伸阅读
            ↓
形成单期 index.md 编排
            ↓
Tomz × Mira 写作
            ↓
事实核验 / 媒体授权检查 / 人类审核
            ↓
正式内容
            ↓
生产发布
```

原则：

> **Mira 负责找与整理，Tomz 负责最终判断。**

发布后：

- 单期 `index.md` 是该期公开编排事实源；
- 详情 Markdown 是各自正文事实源；
- 被引用的既有文章继续以原站原文作为正文事实源；
- 素材库不会成为第二份正式内容；
- shortlist 不自动生成生产页面。

## 8. 索引与站点行为

### 8.1 三层信息架构

见π站点的信息架构确定为：

```text
见π总索引
    ↓
单期编辑索引
    ↓
可选详情文章 / 原站已发布内容
```

对应关系：

```text
/weekly                 # 当前预览路径，最终路径仍 TBD
/weekly/001             # 单期编辑索引
/weekly/001/<slug>      # 可选详情文章
https://mira.tomz.io/... # 已发布内容可直接回链原站
https://tomz.io/...      # 已发布内容可直接回链原文
```

最终路径可以调整，但三级关系本身不再视为 UI TBD。

### 8.2 总索引自动派生

见π总索引页必须从各期正式 `index.md` 自动派生，不维护独立人工 index 数据。

```text
各期 index.md
    ↓
content parser
    ↓
识别见π期刊索引
    ↓
按 issue / date 排序
    ↓
见π总索引页
```

禁止新增需要人工同步维护的：

- `weekly.json`
- `issues.json`
- `jianpi-index.yml`
- 其他重复记录标题、期号、日期、URL 的全站索引文件。

### 8.3 单期索引由 index.md 决定

单期页面不能根据详情文章目录自动猜测编辑顺序。

它必须尊重该期 `index.md` 的人工编排：

- 哪一篇是封面；
- 哪些内容有详情；
- 哪些内容只留短评；
- 哪些内容直接回链已经发布的原文；
- 哪些内容并列；
- 哪些内容只放进“继续看”；
- 页面顺序与权重。

这部分属于编辑判断，不交给文件名排序或自动化推断。

## 9. 媒体与图片出版规则

见π可以使用原始项目、机构、历史档案与开放科学材料中的图片，但“技术上能加载”不等于“可以正式出版”。

### 9.1 默认策略

按以下优先级处理：

1. **明确开放许可或公共领域素材**：核对授权后，由 Tomz.io / R2 自托管，并保留来源与必要署名；
2. **版权不明确或不适合复制的素材**：不搬运，改做见π自己的编辑视觉；
3. **商业媒体、论文出版社、公司品牌视觉**：默认不复制，除非存在明确授权依据；
4. **外站热链**：不作为正式长期资产的默认方案。

### 9.2 编辑视觉

核心文章在无法安全复用原图时，可以使用见π自制编辑视觉，例如：

- 关键数字；
- 时间对照；
- 引文关系；
- 简单图形；
- 结构图；
- 经许可的公共素材再编辑。

编辑视觉的目的不是“每篇都做海报”，而是保证重要内容拥有稳定、统一、可长期保存的视觉表达。

对于“已发布内容 / 延伸阅读”，原则上优先复用原文自身已经合法发布的封面引用方式或只使用文字链接；不因为进入见π而重复搬运一套媒体资产。

### 9.3 出版检查

正式发布前，涉及图片至少确认：

- 来源；
- 授权 / 公共领域状态；
- 是否需要署名；
- 是否允许修改；
- 本站托管位置；
- 原始来源链接。

原则：

> **宁可没有图，也不把版权不清楚和随时可能失效的外链当成长期出版资产。**

## 10. UI / 视觉

v0.3 确定信息架构，但仍不锁定具体视觉设计。

已经确定：

1. 见π总索引负责展示历期；
2. 单期页面首先是“编辑索引 / 杂志目录”，不是默认全文阅读器；
3. 单期索引必须允许不同内容权重：封面文章、编辑文章、短讯 / 鬼集、已发布内容 / 延伸阅读等；
4. 详情页只在真正需要展开时存在；
5. 已经上线的 Mira 周报、工作与生活周记等允许以“链接 + 简介”直接进入单期索引；
6. 见π可以比 Tomz.io 主站整体气质更外放；
7. 不能破坏全站 Header、主题、可访问性与基础 token；
8. 不得因为见π UI 施工导致博客、书架、项目、作品、关于等既有页面视觉或功能回滚；
9. 当前 `preview/weekly-v0-1` 的 UI 仅视为实验实现，不视为最终设计。

v0.3 仍不规定：

- 杂志式 / 卡片式 / 封面墙的具体视觉表现；
- 每期主色；
- 字体特殊化；
- 动效；
- “Signal / Radar”式视觉语言；
- 当前预览页面的任何具体版式。

## 11. 生产安全边界

这是 v0.3 的硬约束。

### 11.1 禁止整枝合并旧施工分支

当前：

```text
main
preview/weekly-v0-1
```

已经经历过独立演进。

因此：

> **禁止将 `preview/weekly-v0-1` 整枝直接 merge 回 `main`。**

正式发布时必须：

1. 从最新 `main` 新建干净集成分支；
2. 只迁入已经确认的见π能力；
3. 保留 main 当前全部内容与既有功能；
4. 对共享 Header、书架、路由、PWA、静态输出进行回归；
5. 通过人类验收后再进入 main。

### 11.2 main 是生产事实基线

任何集成不得使以下内容倒退：

- 已发布文章 / 书籍章节数量；
- 书架封面与布局；
- 博客 / 投稿 / 项目 / 作品 / 关于；
- Header 与 active 状态；
- 搜索；
- 主题切换；
- PWA；
- sitemap；
- canonical；
- JSON-LD；
- 内容发布时间 / 修改时间；
- GitHub Pages 与生产域名的路径兼容。

### 11.3 Preview 不能覆盖生产事实

预览分支允许实验，但如果与 `main` 不一致：

> **以最新 `main` 的既有功能和内容为保留基线。**

见π的新增价值不能以回滚 Tomz.io 已有能力为代价。

### 11.4 已发布内容不制造重复正文

将 Mira 官网、Tomz.io 或其他正式维护站点中的既有文章编入见π时：

- 不复制正文；
- 不创建可索引的平行全文页；
- 不改变原文 canonical；
- 不伪造新的发布时间；
- 见π只承担编辑简介与导航关系。

## 一句话定义

> **见π是 Tomz × Mira 持续观察外部世界、从噪声中留下值得继续看的技术、产品、开发者、研究、历史与异常信号，并通过一期一次编辑把它们组织成可长期保存内容的独立产品。**

## 内容模型一句话

> **一期不是一篇文章，而是一次编辑；单期索引是编排事实源，详情文章只为值得展开的内容存在，已经发布的内容则回到它原本的正文。**
